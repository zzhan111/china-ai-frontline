# 公众号长文 Contract — Building Blocks v0

> **状态：building block，不是正式 contract。​** 这里只累积“长文级”的写作维度与红线，等积累 ≥2–3 篇长文实战后再编译成可评分的 `contracts/longform/v1.md`（仿 `contracts/posts/v1-common.md` 的评分骨架）。
>
> **为什么单列 longform：​**`contracts/posts/`（X / 小红书 / 朋友圈）管的是**短社媒**——前 3 秒钩子、信息密度、平台原生。公众号长文（人物特稿 / 意见判断 / 热点调研）的成败维度不一样：它要的是**活人感、与读者的内在对话、叙事节拍、概念藏进经历、克制、事实密度、公共判断**。短社媒 contract 的“AI 痕迹清单”仍然适用（继承），但不足以评一篇公众号长文。
>
> **继承关系：​** longform extends `contracts/posts/v1-common.md` 的 §3 硬性禁区 + §4.4 AI 痕迹清单 + 001 宪法（`raw/2026-05-12-cowork-001-article-constitution.md`）的“观察者姿态 / 不下结论 / 无归纳清单 / 无公众号自指”红线。下面只加**长文特有**的维度。

## 长文的三种子类型（先定类型，再套维度）

长文不是单一体裁。到 006 为止跑通三类，成败维度**同源但表现形态不同**：

| 子类型 | 代表 | 主体 | 成功长这样 | 失败长这样 |
| --- | --- | --- | --- | --- |
| **A 人物特稿** | 004 | 一个人 | 人物立起来，读者“看见”他 | 履历罗列、流水账 |
| **B 意见/判断型** | 005 | 一个判断 | 判断清楚、能被读者带走 | 产品流水账、术语墙 |
| **C 热点调研型** | 006 | 一个事件 / 争议 | 事实可靠、边界清楚、能从热点升到公共判断 | 跟风复述、资料堆砌、阴谋论化、过期新闻 |

**用法**：先判定本篇是 A、B 还是 C，再套 LF 维度。LF-1～LF-6 三类都要过，但判据按类型落地（下面每条标 `A:` / `B:` / `C:`）；LF-7～LF-9 是 **B / C 共用的判断型维度**（A 选配）；LF-10～LF-12 是 **C 专属**。

## 长文特有维度（每条：判据 + A 人物特稿样本 + B 意见型样本 + C 热点调研型样本）

### LF-1 活人感（抽象是否“立起来”）

**判据**：抽象（人物 / 论点 / 事件）必须落到**具体动作 + 细节**，读者能“看见”，而非属性 / 履历 / 论点 / 资料罗列。

- `A` 人物靠**具体动作 + 真实对白 + 感官细节**呈现。
  - 反例：004 v1·写外挂的少年：事件一笔带过，“他写完外挂喜欢免费往外发”——是概述，不是场景。
  - 正例：范文：宿舍“脚臭和汗臭夹杂的味道”、床“一有动作就吱呀作响”、尿频只能用“一个粉色的盆”；对白口吻有别（家人 vs 被规训的女孩）。

- `B` 没有主角人物，但判断要落到**具体的人在具体场景里的动作**——用工作镜头验证抽象判断（场景即验证，不是举例凑数）。
  - 反例：005 v1.0/v1.2：判断停在概念层（“个人 Agent 是记忆层 / 调度层”），读者无画面。
  - 正例：005 preview §06“三个人的早晨”：陈翻草稿查旧文找选题、林在地铁上只改一处、周调出三个月前评审会 CTO 的两条反对理由——抽象分工被三个工作镜头坐实。

- `C` 热点不是“新闻条目”，而是要落到**具体用户在具体任务里的体验 / 账单 / 反馈**。
  - 反例：只写“Fable 5 发布，benchmark 全面领先，社区热议”，读者看完仍不知道这件事与自己有什么关系。
  - 正例：006 用“200 美元 Claude Max 月费会员，跑 3 个任务就烧空”“英文社区有人一个 session 三天烧了 4000 美元”“6 月 23 日后从订阅套餐中移除，改为 usage credits 计费”把抽象的“贵”落到用户账单和使用体验。

- **红线（通用）​**：通篇只有“是什么”（属性 / 论点 / 新闻事实）而没有“在做什么 / 发生在谁身上 / 造成什么体验”，判失败。

### LF-2 与读者的内在对话（共情逻辑）

**判据**：叙述贴着**当下推理**走，让读者**同步发现**，而不是被作者预先告知结论；在读者会卡壳处，用“设问→带读者探索”的内在节奏。

- `A` 贴**人物**的当下推理。
  - 反例：004 v1：用户原话“什么时候该以一种‘内在的’对话逻辑来共情读者，隐藏在文本中带着读者去探索”——v1 缺这个。
  - 正例：范文：“素伶心想，管这么严，说不定表弟真摊上了大事”——读者跟着她推理，一起被骗、一起醒悟。

- `B` 全文由**一个读者也会问的问题**驱动，答案分步推进，不一次性抛结论。
  - 正例：005：核心问题“平台都把能力打包好了，一个人还需要‘自己的’ Agent 吗？”——先答“需要”，再层层推进（不是因为更强 → 平台该赢 → 但差那 20 分 → 配置要消失 → 两者协作）。

- `C` 全文由**热点发生后读者真正会追问的几个问题**驱动：它是真的吗？它强在哪里？边界在哪里？为什么这么贵？这件事说明什么？
  - 正例：006 的推进顺序不是“发布新闻 → 参数 → 价格 → 总结”，而是“它确实很强 → 但封神有边界 → 真正的刺客不是标价，是长任务 → 静默降级才是真正的不平等 → 中文圈看到另一层问题 → 这不是一次模型升级，而是一次订阅体系调整”。
  - 原则：热点调研型文章不怕结论明确，但结论要跟着读者疑问逐层出现。

- **红线（通用）​**：一上来就抛完整结论、把读者当听众而非同行者，判失败。

### LF-3 概念锚定（术语藏进经历 / 场景，不科普）

**判据**：陌生概念**首次出现处**必须让读者懂——优先靠**一个具体场景 / 类比 / 读者侧后果**让概念被“撞见”，其次才是一句白话括注。绝不堆术语。

- `A` 术语藏进经历。
  - 反例：004 v1·01 节：用户批“什么是‘反应釜’”没解释；“面壁智能”无注释。
  - 正例：范文：全程不科普“戒网瘾机构是什么”，靠验孕棒、迷彩服、叠豆腐块军被、洗澡要“特批”让读者自己懂。

- `B`（尤其科技意见文）除“藏进场景”外，还要把**技术词翻译成读者能感到的负担 / 收益**，而非科普协议本身。
  - 反例：005 v1.2：MCP / CLI / workflow / 自托管密集出现，准确但劝退。
  - 正例：005 preview 的翻译表：

| 技术表达 | 发布稿表达 |
| --- | --- |
| MCP / CLI | 后台连接、调用外部能力 |
| workflow | 调流程 |
| 自托管 / 本地部署 | 跑在你能控制的环境里 |
| 记忆层 / 调度层 | 记得你、替你判断怎么做 |

并把门槛问题翻成用户问题——“不想为了一个更好的 AI，先变成半个技术人员”。**选词本身就是锚定决策**：005 把“个人 Agent”改成“本地 Agent”，选更贴大众直觉、自带“资料 / 隐私 / 可控”暗示的词。

- `C` 热点调研型文章尤其容易术语过载，必须把 benchmark、usage credits、classifier、token、agentic task、model routing 等词翻成**读者侧体验**。
  - 反例：只解释 safety classifier / PEFT / steering vectors 的技术机制，读者看懂术语但不知道风险。
  - 正例：006 把静默降级翻成“你付的是 Fable 5 的价格，但某些任务实际拿到的是 Opus 4.8 的答案”；把 usage credits 翻成“过去你订阅的是一个 AI 助手，以后你调用的是一台昂贵的智能机器”；把 agentic workflow 翻成“它会读文件、查资料、写代码、跑测试、改错，再循环”。
  - 原则：C 类不是技术科普，而是**用技术事实解释用户处境和产业变化**。

- **操作（通用）​**：术语清单逐个检查首现处有无“读者侧落点”。如果首现处只能靠括号硬解释，说明还没有锚定好。

### LF-4 叙事节拍 / 反流水账（每段有重心）

**判据**：每节 / 每段有一个**重心**，有起伏、有取舍；不匀速平铺、不“看似写了很多却没重点”。

- `A` 每节一个**叙事鼓点**。
  - 反例：004 v1：用户原话“很多地方像流水账一样一笔带过……没有重点”；典型病句“他离开内蒙古到天津的原因……便收住了”——一笔带过却让读者疑惑。
  - 正例：范文：10 个编号小节，每节标题是一句戏剧性引语（“宝宝”/“我们家猫丢了都查监控啊”），每节一个 beat。

- `B` 判断要**分层推进**，产品信息**压成趋势入口**，不逐条罗列功能。
  - 反例：005 v1.1：Coze 3.0 功能写满，读成产品评论。
  - 正例：005 preview：只在开头点 Coze / WorkBuddy / Dumate，立刻升一层到“平台型 Agent 正在变成云端团队”。

- `C` 热点调研要避免“资料夹式写法”。事实很多，但每一层都必须服务一个判断：真伪、能力、边界、成本、机制、产业变化。
  - 反例：把官方 benchmark、HN 反馈、Reddit 争议、中文社区、价格表、API 机制全部平铺，最后加一句“值得关注”。
  - 正例：006 的节拍是“先承认强 → 再指出边界 → 再放大成本 → 再提出静默降级 → 再回到中文圈和工具链 → 最后升到订阅体系调整”。每一节都比上一节高一层。
  - 操作：C 类定稿前逐节标注“这一节解决哪个读者问题 / 推进哪个判断”。标不出来就删、合并或升层。

- **红线（通用）​**：A 出现“一笔带过却让读者更疑惑”的句子（给悬念不给信息，又非有意留白）/ B 退化成“它有哪些功能”的产品流水账 / C 退化成“我搜到了哪些资料”的资料流水账——判失败。

### LF-5 藏与露（张力靠细节，不靠形容词）

**判据**：最大的信息放进最小的细节 / 最克制的判断；用白描和取舍制造张力，而非用“震撼 / 残忍 / 了不起 / 封神 / 爆炸”这类作者形容硬推情绪。

- `A` 把**信息**藏进细节。
  - 正例：范文：“这句话让虚空顿感不妙。他们两人从来不叫对方‘宝宝’。”——两个字引爆悬念；母亲那封 **AI 生成的道歉信**，show 不 tell。

- `B` 藏掉**实现细节**，露出读者要记住的**判断**。
  - 正例：005：藏掉 MCP / CLI / workflow / 自托管 / 多 Agent 技术细节；露出“平台会干活、本地 Agent 懂你、配置不该是用户的工作”。

- `C` 藏掉**调研炫技和资料堆砌**，露出读者需要判断的**边界和后果**。
  - 反例：展示自己查了多少来源、用了多少工具、跑了多少流程，读者看到的是作者工作流，不是事件本身。
  - 正例：006 v1.1 删除“subagent 误判”开头，改用“200 美元跑 3 个任务烧空”“三天 4000 美元 session”“6 月 23 日后移出订阅套餐”直接切入。作者调研过程被藏起来，读者只看到事件造成的冲击和判断链条。
  - 原则：热点调研可以说“我花了 24 小时调研”，但不能把写作脚手架、工具路线、验证流程当成正文戏剧性来源。

- 继承 001 宪法（通用）：观察者姿态、不下结论、结尾定格在画面或一句不解释的话上。

### LF-6 场景调性（人文 / 稳重 > 喧嚣）

**判据**：长文要稳重、引发思考；**商业 / 自媒体 / 直播间 / 路演 / 技术圈狂欢 / 社区情绪的喧嚣感要降为材料**，不作为叙事底色。

- `A` 把采集现场的喧嚣降为脚注。
  - 反例：004 v1：用户原话“直播间确实感到 cheap、虚假、不诚实……抓住深度、还原受访者、设定一个比较稳重、人文主义、引发人思考的场景”。v1 把“直播连麦”写进导语并反复出现。
  - 操作：采集场景（直播间 / 路演 / 黑客松喧嚣）若非主题必需，降为一句脚注；正文锚定在人与思想。

- `B` 判断要落在**日常工作流**，不堆宏大技术叙事或行业口号。
  - 正例：005：写文章前找素材 / 见客户前拼上下文 / 投资人追问时找决策依据——贴近读者真实工作，而非“AI 革命”宏大叙事。

- `C` 热点调研要处理社区情绪，但不能被情绪带跑。要把“炸场 / 封神 / 刺客 / 不平等”翻译成可验证的事实、边界和机制。
  - 反例：全文跟着社区喊“封神”“割韭菜”“阴谋”，没有事实分层。
  - 正例：006 承认“Fable 5 确实很强”，再写“封神有边界”；承认“贵”，再写“真正的问题是长任务成本和订阅体系变化”；写“静默降级”时保持“社区担忧 + 机制风险 + 透明度问题”，避免写成阴谋论。
  - 原则：C 类可以有传播钩子，但底色必须是冷静调研，不是情绪转述。

- **注意（通用）​**：这条与“真实质感 / 非 PR 通稿”红线不冲突——诚实交代信息来源仍要，但**不渲染**喧嚣场景、**不喊**口号。

## B / C 判断型共用维度（A 选配；来源：005、006）

### LF-7 观察 → 公共判断（不要停在“它有什么功能 / 发生了什么”）

**判据**：判断型长文必须把**一个具体观察**（某产品 / 事件 / 争议）升级成**可迁移的判断**。读者带走的不是“X 发布了什么”，而是“X 让什么分工 / 旧假设 / 趋势变清楚了”。

- `B` 意见型：
  - 反例：005 v1.1：Coze 3.0 写成全文主角 → 读者读成单一产品评论。
  - 正例：005 preview：Coze 3.0 / WorkBuddy / Dumate 降为开头观察入口，正文统一”平台型 Agent”，全文讨论”平台型 vs 本地 Agent 的新分工”。
  - 正例：007：两个独立信号（Jarred 的 6 步开发闭环 + x402 的 creator marketplace）各自讲清后，合并升级为”Agent 经济的完整回路已经闭合”——读者带走的不是”Bun 做了什么”或”x402 是什么”，而是”Agent 从能干活到能赚钱的回路，已经在搭了”。

- `C` 热点调研型：
  - 反例：006 如果只写成“Fable 5 发布 24 小时内各方反馈汇总”，就是新闻搬运。
  - 正例：006 把 Fable 5 发布升级成“前沿模型正在从互联网会员产品变回云计算资源”“AI 订阅体系调整的预演”“模型越强、越贵、越不透明，越需要工具链 / 预算控制 / 观测层 / 路由”。
  - 操作：C 类定稿前自问四句——这个热点说明了什么？它让哪种旧体验失效？它让哪种新成本显性化？它会改变哪一层产业分工？

- **红线**：通篇停在“它有哪些功能 / 社区怎么说 / 价格是多少”，没有升一层到公共判断，判失败。

### LF-8 传播锚点 / 一句能被带走的话

**判据**：要有**一句金句**同时承担三个功能——概念解释 + 文章主线 + 传播记忆点；读者转发时能原样带走这一句。

- `B` 意见型：
  - 正例：005：”平台型 Agent 的优势是：它会很多事。本地 Agent 的优势是：它知道你的事。”——一句锚定两个概念、给出全文判断、可被原样转发；结尾再压一层：”平台负责能力。本地 Agent 负责上下文。真正的智能，发生在两者之间。”
  - 正例：007：”工厂再大，东西卖不出去，它只是一个车间，不是一个经济体。”——用一个所有人都能秒懂的类比，把”生产端+流通端=完整回路”的整篇论证压缩进 25 个字。这篇的第二金句是结尾：”不是'将要发生'。是正在发生。”——九个字，不用任何术语，给读者一个确切的时空锚点。

- `C` 热点调研型：
  - 正例：006：“封神是真的，但这是一个限定版的封神。”“短任务看能力，长任务看链条。”“贵至少是透明的。真正麻烦的是静默降级。”“过去你订阅的是一个 AI 助手，以后你调用的是一台昂贵的智能机器。”“模型封神只是新闻。谁能把神请进生产系统里，还不把账单烧穿，才是下一阶段真正的能力。”
  - 原则：C 类金句必须从事实链条里长出来，不能只是情绪标题。比如“模型封神只是新闻”成立，是因为前文已经完成了能力、边界、成本、透明度和工具链的层层铺垫。

- **注意**：金句 ≠ 营销式“不是 X 是 Y”空话（仍受 `v1-common §4.4` AI 痕迹清单约束）。金句必须**承载真实判断**，靠区分度而非修辞对仗成立。
- **操作**：定稿前找出“如果读者只记一句，是哪句”；若找不到，说明判断还没锚定。

### LF-9 立场公允 / 反稻草人（先扬后立）

**判据**：亮出己方判断前，先**诚实承认对立面或热点对象的合理强项**（steelman），再谈边界、代价和自己的判断。先扬后立比直接对立更可信。

- `B` 意见型：
  - 反例：把平台写成反派、把”本地 Agent”写成救世主 → 二元对立，读者不买账。
  - 正例：005 §02：单设一节”平台会吃掉大多数通用任务，这是好事”——“平台型 Agent 该赢……AI 终于从 demo 变成了基础设施”，先把对手抬到合理位置，§03 再给出”差的就是那 20 分”。
  - 正例：007 §5”说实话的部分”：用另一种公允形式——不是承认对立面强（本文没有对立面），而是**承认自己判断的保质期有限**。明确列出 x402 生态薄、加密摩擦高、Jarred 范式只在编程场景被验证、6-12 个月内可能被推翻。这种”判断+自我限定”的组合比只给判断更可信，因为它主动暴露了读者可能会问的质疑。
  - 继承 005 选题卡”不贬低 Coze”红线。

- `C` 热点调研型：
  - 反例：为了写反转，开头就说“封神是骗局 / 全是营销 / 用户被割”，会把文章写成情绪批判，事实可信度下降。
  - 正例：006 先完整承认 Fable 5 的能力跃迁：SWE-Bench Pro、SWE-Bench Verified、FrontierCode Diamond、英文社区好评、复杂重构与前端还原实测反馈；随后才写“封神有边界”“成本才是普通用户的真实痛点”“静默降级比贵更严重”。
  - 原则：C 类尤其要避免“为了反转而反转”。热点对象如果真的强，必须先承认它强；只有承认强，后面的边界和代价才可信。

- **红线**：通篇只贬损对立面 / 热点对象、不给对方任何合理性，判失败。

## C 热点调研型专属维度（来源：006；LF-10 经 007 扩展为 B/C 共用）

### LF-10 事实验证优先（先确认真伪，再写判断）—— B/C 共用

**判据**：引用外部事实（数据、⭐数、交易量、协议支持、社区声称）的文章，不论子类型，只要讨论的对象是**冷门 / 新生 / 争议性项目**，就必须先过事实关。不能因为”看起来像真的”就进入判断。

**适用条件**（从 C 专属扩展）：只要满足以下任一条件，B 类意见型文章同样触发 LF-10——①讨论的项目上线不到一年（如 HermesHub、x402 基金会）；②引用的数据来自社区二手转述（如”推文宣称 691 个 skill”）；③数据源可能在文章写作期间已经变化（如 GitHub ⭐数、链上交易量）。

- `B` 意见型（新增）：
  - 正例：007 对 11 项核心事实做了浏览器实时验证后再写判断——HermesHub ⭐数（252 vs 原以为的 230）、skill 数（22 vs 社区声称的 691）、x402scan 月交易量（511 万笔）、协议标准（agentskills.io 而非 MCP）。验证结果写入 published 版的文末附录，同时作为可信度背书和可复现的验证方法。
  - 反例：如果 007 直接沿用素材里的”HermesHub 230⭐ / 691 个 skill / 通过 MCP 发现”，三个数据点全错，文章的核心判断仍然成立，但读者一旦发现事实错误就会连判断一起否定。

- **事实层必须区分**：
  - 官方事实：发布、benchmark、价格、套餐变化、机制说明。
  - 社区反馈：HN / Reddit / V2EX / Twitter / 中文社区中的实测、抱怨、截图。
  - 作者判断：从事实和反馈中推导出的趋势、边界和产业定性。
  - 待验证信息：看似重要但尚未有足够证据的信息，不能写成确定事实。

- **正例（006）​**：
  - 用官方 benchmark 承认能力基础。
  - 用英文社区和中文社区反馈补足真实使用体验。
  - 用价格、usage credits、session 成本解释成本变化。
  - 用官方机制说明与社区担忧共同讨论静默降级，而不是单方面写成阴谋。
  - 把“24 小时调研”作为调研窗口说明，而不是把调研流程写成正文戏剧。

- **红线**：
  - 未核实的传言写成事实。
  - 单条社区反馈写成普遍结论。
  - benchmark 领先直接推导成“全场景替代”。
  - 把争议机制写成确定恶意。
  - 为追热点牺牲事实层级。

- **操作**：C 类定稿前至少做一次“事实标签审查”，给关键句标注：官方事实 / 社区反馈 / 作者判断 / 待验证。凡是标签混乱的句子必须改。

### LF-11 账本 / 机制 / 体验三层拆解

**判据**：热点调研型长文不能只写“强不强”，还要拆出“用户真正承担什么”。对科技热点尤其要同时看三层：账本、机制、体验。

- **账本层**：价格、套餐、token、单任务成本、长任务成本、订阅与 usage credits 的变化。
  - 正例：006 把 \$10/M input、\$50/M output、200K input + 50K output 约 \$4.50、\$20-\$40 per hour、三天 \$4000 session、\$200 Max 跑 3 个任务烧空放在同一成本链条里，结论不是“它贵”，而是“前沿模型从互联网会员产品变回云计算资源”。

- **机制层**：触发条件、降级、分类器、路由、模型分层、平台规则。
  - 正例：006 写 safety classifier / PEFT / steering vectors 争议时，重点不是科普机制本身，而是指出“用户付 Fable 5 价格，却可能拿到 Opus 4.8 答案”的透明度风险。

- **体验层**：用户如何感知这件事，工作流如何变化，普通开发者 / 消费者 / 创业公司会遇到什么问题。
  - 正例：006 把“强模型”落到普通 CRUD、复杂重构、逆向工程、中文写作、长任务烧额度、静默降级不可见等具体体验差异。

- **红线**：
  - 只写能力，不写成本。
  - 只写价格，不写机制。
  - 只写机制，不写用户体验。
  - 只写社区情绪，不写可验证账本。

- **操作**：C 类定稿前检查全文是否至少回答三句话：用户多付了什么？平台机制改变了什么？使用体验因此变成什么？

### LF-12 时效窗口内达到发布标准即发布

**判据**：热点调研型文章的版本策略不同于意见型文章。它追求的是**信息窗口期内达到发布标准即发布**，而不是无限打磨到最优版本。

- **适用条件**：
  - 事件仍在 24-48 小时传播窗口内。
  - 事实核验已达基本发布标准。
  - 主线、边界、成本、争议和公共判断已经闭环。
  - Contract 自检通过，没有硬性禁区问题。
  - 继续打磨的边际收益低于错过窗口的损失。

- **正例（006）​**：
  - 006 从选题卡片 → v1.0 → v1.1 → Published，只经历 2 轮草稿 + 2 次内修订，没有走 002 的“Preview 独立版本 → 定向修订”流程。
  - 原因是 Fable 5 发布 24 小时内是信息窗口期。走 Preview → 修订 → 再发布至少需要额外 6-12 小时，而热点调研型文章的核心价值有一半来自发布时间。
  - v1.1 已达发布标准，Contract 自检通过，正文文字在发布版中 zero-diff。发布时只做 WeChat 编辑器格式化、配图、加粗，不在编辑器里临时改正文。

- **与 B 意见型的区别**：
  - B 意见型更适合多轮 preview、观点沉淀、结构重排。
  - C 热点调研型更适合“事实核验 + 判断闭环 + 快速发布 + 发布后复盘”。

- **红线**：
  - 为抢时效牺牲事实核验。
  - 为追完美错过热点窗口。
  - 在发布编辑器里临时大改正文，引入错误。
  - 没有达到发布标准却用“热点快”作为借口发布。

- **操作**：C 类在 v1.1 阶段做一次”是否发布”判断：若正文已可直接发布，编辑器只做格式化，不再改文字。

## B 意见型专属维度（来源：007；005 为配套样本）

### LF-13 概念继承审查——素材里的术语不能直接进正文

**判据**：意见型文章从选题素材（inbox、评估文档、社区讨论）中继承的核心概念和隐喻，在进入正文前必须过一个”读者视角三问”——①不读素材原文，读者能秒懂这个词吗？②这个词有没有跟日常语言中的另一个意思撞车？③如果去掉这个隐喻，判断本身还成立吗？任一问答”否”，就放弃这个概念，换用所有人都能秒懂的日常词。

**为什么这条维度需要独立存在**：LF-3（概念锚定）管的是”术语出现在正文里怎么解释”——用场景/类比/读者侧后果让读者懂。但 LF-13 管的是更上游的决策——**这个词根本不该出现在读者面前**。素材里的内部术语（框架命名、行业黑话、社区梗）是写作者的脚手架，不是读者的阅读材料。LF-3 能帮读者理解一个词，但不能帮作者判断这个词该不该存在。

- `B` 意见型：
  - **正例（007）​**：
    - 素材继承词：”造车阶段”（来自 long-form-assessment.md 引用的微信文章”修路→造车→收过路费”三阶段比喻）
    - 三问结果：①读者不读那篇微信原文，能秒懂”造车”吗？不能——这个词在 AI 圈没有约定俗成的含义。②和日常语言撞车吗？撞——“造车”在中文里的默认意思是汽车制造。③去掉比喻后判断还成立吗？成立——“两个信号证明 Agent 经济的完整回路已经出现”完全不依赖”造车”这个词。
    - 决策：全文放弃”造车”，改用”Agent经济的完整回路”（核心概念）和”干活/赚钱”（叙事语言）。
    - 这个决策不仅改变了用词，还改变了标题方向——如果保留”造车”，标题会变成”造车阶段的两张入场券”，读者必须先理解框架才能进入正文。
  - **反例（假设）​**：如果 007 保留了”造车阶段”，流程是——读者要先知道”修路→造车→收过路费”三段论（认知跳转 1），再接受”Agent 工具链 = 造车”的比喻映射（认知跳转 2），然后才能进入正文的实际论证。两层跳转，每层都会流失读者。
  - **与 LF-3 的分工**：LF-3 处理”必须出现但需要解释的词”（如”本地 Agent”→”跑在你能控制的环境里”）。LF-13 处理”可以不出现在读者面前的词”。两者不重叠——一个词如果通过了 LF-13 的审查，再进入 LF-3 的锚定流程。

- `A` 人物特稿：选配。人物特稿的概念通常来自受访者本人而非外部素材框架，此问题较少出现。但如果引用了”行业术语框架”来描述人物（如”他是一个典型的第二曲线创业者”），同样触发——“第二曲线”对不读管理学的读者可能毫无意义。

- `C` 热点调研型：选配。C 类也有从社区情绪中继承的流行词（”封神””刺客””割韭菜”），处理方式不同——C 类可以把这些词材料化（”社区喊封神，但……”），而不是直接用它做自己的叙事框架。但 C 类对时效窗口有要求，不要求像 B 类一样在标题阶段就完成概念审查。

- **红线**：通篇使用一个读者不读素材就无法理解的隐喻/框架做核心概念，且没有在写作过程中做过”读者能秒懂吗”的检查，判失败。
- **操作**：定稿前列出全文从素材继承的概念词清单，逐个过三问。标出哪些是”正文概念词”（读者必须懂的）、哪些是”写作脚手架词”（读者不需要知道的）、哪些是”被放弃的词”（如”造车”）。

## 新增通用红线：个人工作流痕迹不得进入正文

**判据**：正文不得包含本文撰写过程中 AI / agents / 工具链参与的工作流描述。这些内容属于作者的写作脚手架，不是读者需要知道的信息。

- **禁止进入正文的内容**：
  - “我让几个 agent 分头查证……”
  - “某个 agent 第一轮判断错了……”
  - “它们的知识截止在某个时间……”
  - “我用某工具打开页面后发现……”
  - “我的写作流程是……”
  - “这段是由某工作流生成 / 校验 / 合并的……”

- **允许保留的中性表达**：
  - “我花了 24 小时调研……”
  - “我核验了官方页面、社区反馈和定价机制……”
  - “根据公开资料和社区实测……”
  - “在发布 24 小时内，几个信号已经足够清楚……”

- **正例（006）​**：
  - v1.1 删除原开头中“3 路 subagent 分头查证 Fable 5 是否真实存在”的段落。
  - 替换为“200 美元 Claude Max 月费会员，跑 3 个任务就直接烧空”“英文社区里有人一个 session 三天烧了 4000 美元”“6 月 23 日之后，Fable 5 将从订阅套餐中移除，改为按 usage credits 计费”。
  - “24 小时调研”保留，因为它是中性的调研窗口说明，不暴露具体工具和流程。

- **原则**：读者需要看到的是事实、场景、判断和后果，不是作者如何调用工具完成写作。写作脚手架只应进入 `evolution.md`，不得进入正文。

- **个人工作流痕迹**：本文件新增为 longform 通用红线；正文不得出现 AI / agents / 工具链参与写作的过程描述。

## 升级为正式 contract 的触发条件

- 已有 004（A 人物特稿）+ 005（B 意见型）+ 006（C 热点调研型）+ 007（B 意见型）四个样本，覆盖三种子类型。
- LF-1～LF-6 已有 A / B / C 三类样本；**LF-7～LF-9 已有 B 类两个正例（005 + 007）✅ 触发 v1 编译条件**；LF-10～LF-12 目前只有 006 一个正例。
- 触发 v1 编译：当每条维度（按其适用类型）都至少有 **2 个独立病例 / 正例**时：
  - A 人物特稿：需再有一篇人物类长文补齐 LF-1～LF-6 的稳定判据。
  - B 意见型：**✅ LF-7～LF-9 已触发（005 + 007）**；LF-13（新增，B 专属）目前只有 007 一个正例，需再有一篇 B 类验证。
  - C 热点调研型：需再有一篇热点调研型长文验证 LF-10～LF-12。
