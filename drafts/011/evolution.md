## 2026-06-16 — v1.2 → published：用户发现 18.5x 数字错误 + 微信发布版抓取

### 做了什么

**18.5x 数字溯源与修复**：
- 用户追问："**2026 年目标是 18.5 倍** 18.5倍数字哪里来的？哪个数字的18.5倍？"
- 追溯计算链：正文中 "2024 年优必选卖掉了 1,079 台"（公司全年总出货）+ "现在他们对同一个客户的 2026 年目标是 18.5 倍" → 20,000 ÷ 1,079 ≈ 18.53
- **错误本质**：分子是比亚迪年目标（20,000），分母是优必选全年全量出货（1,079）。"同一个客户"的措辞让读者以为在比"比亚迪今年 vs 比亚迪去年"，实际上在比"一个客户的目标 vs 整家公司去年的总产量"。这是**分母用错了对比对象**。
- 正确的三个数字：

| 分子 | 分母 | 得数 | 是什么 |
|---|---|---|---|
| 20,000 | 1,079 | 18.5 | 单客户目标 ÷ 公司去年全量（原错误用法） |
| 20,000 | 150 | **133** | 单客户目标 ÷ 同一客户去年采购（应使用） |
| 20,000 | 90+ | ~222 | 单客户 Walker 目标 ÷ 同一客户去年 Walker 采购 |

- **修复**：正文 "18.5 倍" → "133 倍"；表格中的 "18.5x 跳跃" 保留——表格比较的是目标与公司去年全量，分母不同，语境自明。
- **为什么三轮 contract review（94→99→102）都没发现？** 因为 review 的焦点在 LF-1~LF-12 的写作维度上，没有逐字验算每个数字的对比对象是否成立。这暴露了 contract 系统的一个盲区：**对比类数字（"X 是 Y 的 N 倍"）的分母对象不应该只靠作者自检，应该作为 fact-check 的独立核查项**。

**微信已发布版抓取与 published.md 生成**：
- 用户提供微信文章链接 → browser 打开 → snapshot 提取全文
- 发现微信发布版已完成 18.5x→133 倍修复（说明在 draft v1.2 和微信发布之间的某个环节，这个错误已被发现并修正）
- 从微信发布版提取格式化模式：
  1. **导语独立粗体段**："U1，10天，3800台。这是全球所有公开信息中，最大的一次 C 端人形机器人单次预售事件。"——在全文开头单独成段，不等同于传统 journalistic lede，而是将最核心的数字判断浓缩成一句可截图传播的粗体短段
  2. **CEO 引语独立 pull-quote**："我不想简单做一个性爱机器人。"——从嵌入段落中提取为独立粗体段
  3. **章节标题多行拆分**：draft 中的 `**01**` 单行 → 微信中 `**1**` 独占一行，后跟多行粗体标题（每行一个 `<p>`）。原因：微信编辑器逐行渲染粗体，多行标题看起来像设计排版
  4. **核心判断句短段化**："他们买的，大概率是一种介于人与宠物之间的陪伴。" 从正文段落中提取为独立粗体段落。读者在滑动中撞到这些短句时会停下来读
  5. **表格原样渲染**：可信度对比表在微信中为原生 `<table>`
  6. **参考资料精简**：从 draft 的详细 URL + 核验注文，精简为出处 + 核验状态。微信读者离参考资料更远（需要滑到文末），过长会劝退
- 生成 `drafts/011/published.md`（199 行 / 7,210B），content 与微信发布版一致，markdown 使用微信格式化模式

### 学到什么

**关于数字对比的自我审查**：
- 任何 "A 是 B 的 N 倍" 句式，必须在同一句话里显式写出 A 和 B 各是什么。如果读者需要自行推断 A 或 B 的值，这个数字就是有问题的。
- "同一个客户" + 倍数的组合是高危句式。它天然会让读者把分子和分母都锚定到同一个客户身上。如果分母不是客户的数字，必须改写。
- Contract review 的十二维度里没有一个专门检查"对比类数字的分母对象是否成立"。这可能是 LF-10 的扩展方向，也可能是独立的 fact-check 步骤。

**关于 draft → published 的格式转换**：
- 微信的排版不是"把 markdown 渲染成 rich text"。它是一种完全不同的信息节奏：短段、粗体、留白。读者在手机上滑动阅读，不是扫描。
- draft 中的 `**bold**` 在微信中有两种命运：(a) 保留为粗体强调，或 (b) 升级为独立段落。升级的判据是——这句话如果截图发朋友圈，能不能独立成立？能→独立段落；只是段落内的强调→保留行内。
- 表格在微信中可以用的前提是列数 ≤3、每格 ≤15 字。011 的对比表（3 列 × 7 行）刚好在这个边界内。
- 参考资料在微信中的位置是"滑到底才能看到"，和 draft 中 `[n]` 引注被读者随时瞄到的阅读路径完全不同。draft 中有 21 条，published 精简为出处+核验状态，不用删除核心差异信息（如 [21] 的 Zhihu vs Sixth Tone 差异依然保留），但要去掉长 URL 和"文中所引…均来自此报告"的重复说明。

**关于工具链的盲区**：
- 18.5x 这个错误通过了三轮 contract review（v1.0→v1.1→v1.2），被用户用一句话指出来。contract review 的 AI agent 擅长检查文风、结构、信源是否标注——不擅长做小学数学验算。
- 32cm 假数据通过了 v1.0 作者本人和 v1.1 contract review 两轮，最终被 Sixth Tone 的外部验证纠正。
- **这两个错误的共同特征**：都在读者不需要外部知识、只需要停下来想一想就能发现的位置。它们不是因为信息不足而错，是因为作者和 review agent 都没有"停下来想一想"。

**关于迭代的意义**：
- v1.0→v1.1→v1.2 的三轮 contract review 把文章从 94 推到 102，但没有发现 18.5x 的错误。用户的一句追问做到了。这呼应了 evolution v1.1 里写过的那句话："Contract review 的评分不是目的，是指向盲区的探照灯。"——但探照灯照不到的地方，需要人类的直觉和追问来补。

### 还没 close 的 open item
