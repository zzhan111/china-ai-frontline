## 01 选题来源

本篇选题最初来自 `inbox/2026-06.md` 中对 Coze 3.0 的产品观察。

最早的素材判断是：Coze 3.0 不再只是一个低代码 bot 平台，而是在把 Agent 产品形态推向"AI 团队"。它强调多 Agent 协作、项目空间、任务拆解、长期上下文、本地 Agent 接入、CLI/MCP 集成等能力。

这个产品变化触发了一个更大的问题：

> 当平台已经把模型、技能、项目空间、云端算力和工具接入能力都打包好，一个普通人还需要自己的 Agent 吗？

最初的问题表述偏产品分析和 builder 视角，关注点是"大厂平台会不会吃掉工具型 Agent / 个人 Agent 的空间"。后续经过多轮调整，文章逐渐从 builder 视角转向使用者视角，最终落到一个更适合公众号读者的判断：

> 平台型 Agent 的优势是：它会很多事。  
> 本地 Agent 的优势是：它知道你的事。

这个判断成为全文的中心句。

## 02 版本演进概览

### V0：产品观念映射阶段

最早阶段的素材重点是 Coze 3.0 的产品方向。

当时的核心判断是"平台 Agent 和工具型 Agent 会分层共存"。平台负责模型、算力、技能和分发，工具型 / 个人 Agent 负责更细分的场景和个性化工作流。

这个阶段的问题是：判断虽然成立，但太像产品分析笔记，读者对象更像 AI builder，而不是普通公众号读者。文章如果直接从这个角度写，容易变成"Agent 生态位分析"，而不是一篇有公共表达价值的意见文章。

这一阶段形成了两个重要素材：

1. Coze 3.0 是平台型 Agent 走向"云端团队"的代表案例。
2. 平台越强，个人 / 本地 Agent 的位置反而越清楚。

---

### V1.0：长文初稿阶段

V1.0 试图把 inbox 里的产品观察升级成长文。

这一版的主要方向是解释 Coze 3.0 的产品变化，并推导"平台 Agent 与个人 Agent 不是替代关系，而是分层关系"。

但 V1.0 存在几个明显问题：

第一，开篇铺垫过长。文章前 10% 花了较多篇幅交代 Coze 3.0 的背景，但没有足够早地抛出核心判断，导致读者进入速度偏慢。

第二，builder 视角过重。文章在讨论平台、工具、MCP、CLI、生态位时，更像写给开发者或 AI 产品从业者，而不是面向"海外华人读者"的公众号意见文。

第三，个人 Agent 的定义不够清楚。文章提到了"个人 Agent 是记忆层与调度层"，但对普通读者来说，这个说法仍然偏抽象，缺少生活化解释和具体使用画面。

这一版的主要价值，是建立了文章的基本骨架：

> 平台提供能力，个人 Agent 持有上下文并调度能力。

---

### V1.1：强化 Coze 3.0 客观信息阶段

V1.1 根据反馈，重点补充 Coze 3.0 的客观产品信息。

这一版详细介绍了 Coze 3.0 的几个关键信号：

- 它把 Agent 包装成"AI 团队"，而不是单个 bot。
- 它强调多 Agent 协作和项目空间。
- 它允许在同一个项目里让多个 Agent 交接任务。
- 它展示了本地 / 自托管 Agent 接入能力。
- 它对开发者开放 CLI / MCP 集成，同时对新手强调"一键安装"。

这让文章的产品观察基础变得更扎实。

但 V1.1 的问题也随之出现：Coze 3.0 被写得太像全文主角，文章容易被读者理解为一篇 Coze 3.0 产品评论，而不是一篇关于 Agent 新分工的趋势判断。

同时，个人 Agent 的部分仍然不够对等。平台型 Agent 被介绍得很具体，但个人 Agent 仍停留在概念层，读者能理解平台做了什么，却不一定能理解"自己的 Agent"到底是什么、在哪里、怎么用。

---

### V1.2：补足个人 Agent 定义与场景阶段

V1.2 的重点是补足"个人 Agent"的定义和使用场景，使其与 Coze 3.0 的介绍篇幅对等。

这一版新增了专门章节《什么是个人 Agent》，从几个维度解释它：

- 它可能跑在自己的电脑、NAS、私有服务器或自托管环境里。
- 它能够接触用户自己的草稿、文档、客户记录、会议纪要。
- 它不只是一次性对话，而是有长期记忆。
- 它通过 MCP / CLI 等方式调用外部能力。
- 它不复制平台的广度，而是作为记忆层和调度层存在。

V1.2 还扩写了三个具体场景：

1. 写作者：本地 Agent 读取历史文章、草稿和选题记录，再调用平台能力补资料。
2. 销售：本地 Agent 聚合 CRM、邮件、聊天记录，再调用平台工具生成客户方案。
3. 创业者：本地 Agent 记录会议和决策脉络，在投资人追问时调出历史依据。

这一版显著增强了"活人感"。人物不再只是类型标签，而有了更具体的工作处境：

- 陈是断更一年后复更的中文科技账号作者。
- 林是同时使用飞书、企微、CRM、邮件的客户成功。
- 周是做智能硬件出海、正在谈 A 轮的创始人。

V1.2 的主要问题是篇幅过长，技术解释仍然偏多。MCP、CLI、workflow、自托管等术语虽然准确，但对普通公众号读者来说信息密度过高，容易造成阅读负担。

---

### V1.3：意见型发布稿阶段

V1.3 是最终定稿方向，也是 `preview.md` 的基础。

这一版不是继续补充细节，而是进行体裁转换：从"产品分析长文"改为"意见型公众号文章"。

核心调整有四个。

#### 1. 用"本地 Agent"替代"个人 Agent"

"个人 Agent"虽然准确，但语义偏抽象，容易被理解为"我在某个平台上创建的私人 bot"。

"本地 Agent"更接近大众直觉。它让读者立刻感受到：这个 Agent 更靠近我的电脑、资料、工作流和隐私边界。

在发布稿中，本地 Agent 被定义为：

> 它的核心特征不是"在哪里创建"，而是"属于谁、跑在哪里、记得什么"。

这个定义避免了把"本地"狭义理解为必须运行在电脑本机上。文章明确写到，它可以跑在电脑、私有服务器、NAS，或者任何一个用户能控制的环境里。

这样既保留了技术准确性，也降低了读者理解成本。

#### 2. 用"平台型 Agent"替代反复点名 Coze 3.0

V1.3 将 Coze 3.0 从全文主角降级为观察入口。

发布稿开头仍然点到 Coze 3.0、WorkBuddy、Dumate，但后文统一使用"平台型 Agent"来概括这一类产品。

这一调整非常关键。

因为文章真正要讨论的不是 Coze 3.0 这一个产品，而是一类大厂云端 Agent 的共同趋势：它们正在从聊天框变成云端团队，负责拆任务、调工具、交付结果。

这样处理后，文章的公共性更强。读者不会把它读成单一产品评论，而会把它读成一篇关于 AI 助手未来形态的判断。

#### 3. 弱化技术术语，强化使用者感受

V1.2 中大量出现 MCP、CLI、workflow、本地部署、自托管等词。它们对技术读者有帮助，但会让公众号普通读者感到"这篇文章突然变重"。

V1.3 中，这些词被替换为更生活化的表达：

- "接工具"
- "设权限"
- "调流程"
- "后台连接"
- "调用平台能力"
- "哪些信息可以传出去，哪些只能留在本地"

尤其是第 04 节《配置不该是用户的工作》，进行了重点重写。

原来的技术表达是：用户不应该被要求理解 MCP、CLI、workflow，配置应该逐渐消失。

发布稿改成：

> 他们不是不需要更好的 AI，而是不想为了一个更好的 AI，先变成半个技术人员。

这句话更符合意见型文章的表达方式。它把技术门槛问题转译成普通读者能共情的使用负担。

#### 4. 控制篇幅，保留场景亮点

V1.3 将篇幅明显压缩，但保留了最有画面感的第 06 节《三个人的早晨》。

这一节是发布稿的重要亮点，因为它把抽象判断落到了具体的人身上：

- 写作者陈：从历史文章和草稿中找回写作状态。
- 销售林：在见客户前拼回客户关系的上下文。
- 创业者周：在投资人追问时调出历史决策脉络。

这三个场景承担了文章最重要的"验证"功能。

它们不是单纯举例，而是在证明全文判断：

> 本地 Agent 的价值，不是替代平台干活，而是带着你的上下文，去调用平台能力。

发布稿最终保留了这些场景，但删去了过多技术操作细节，让每个场景更像一个工作镜头，而不是产品功能说明。

## 03 发布稿结构

最终发布稿采用 7 个部分。

### 开头：提出核心问题

开头从平台型 Agent 正在变成"云端团队"写起。

通过 Coze 3.0、WorkBuddy、Dumate 作为观察样本，引出一个问题：

> 当平台已经把所有能力打包好，一个人还需要"自己的" Agent 吗？

然后直接给出答案：

> 需要。  
> 但原因不是本地 Agent 会比平台更全、更强。恰恰相反。本地 Agent 的价值不在"会多少事"，而在"知道你的事"。

这个开头相比早期版本更短，也更快进入核心判断。

---

### 01 什么是本地 Agent

这一节负责给读者建立概念。

它没有展开复杂技术定义，而是用三个问题框住本地 Agent：

- 属于谁？
- 跑在哪里？
- 记得什么？

最终把本地 Agent 定义为"更懂你的工作入口"。

这比"记忆层与调度层"更适合普通读者。

---

### 02 平台会吃掉大多数通用任务，这是好事

这一节避免文章变成"反平台"叙事。

发布稿明确承认：平台型 Agent 会吃掉大量通用任务，而且这是好事。

因为平台型 Agent 把门槛压低，让普通人不需要配置、不需要理解技术细节，就能直接使用 AI。

这一节的核心判断是：

> 平台型 Agent 该赢。如果平台不赢，说明 AI 还没进入普通人的日常工作。如果平台赢了，说明 AI 终于从 demo 变成了基础设施。

这句话让文章立场更平衡：不是本地 Agent 对抗平台型 Agent，而是两者在不同层次上分工。

---

### 03 但有些工作，差的就是那 20 分

这一节是全文的价值拐点。

平台型 Agent 能把很多通用任务做到 70 分，但有些工作 70 分不够。

典型例子包括：

- 代表账号风格的文章。
- 发给关键客户的跟进邮件。
- 影响产品路线的会议总结。

这些工作的问题不在于 AI "会不会做"，而在于 AI "了不了解你"。

这一节落下全文最重要的金句：

> 平台型 Agent 的优势是：它会很多事。  
> 本地 Agent 的优势是：它知道你的事。

---

### 04 配置不该是用户的工作

这一节回应了本地 Agent 最大的现实障碍：配置门槛。

早期版本容易把问题写成技术问题，但发布稿把它写成使用意愿问题。

普通用户不是不需要更好的 AI，而是不想为了更好的 AI，先变成半个技术人员。

因此，本地 Agent 想进入大众市场，关键不是让更多人学会配置，而是让配置消失。

这一节完成了从"技术趋势"到"产品判断"的转换。

---

### 05 新的分工

这一节把全文判断压缩成清晰分工：

> 平台型 Agent 负责"能不能做"。  
> 本地 Agent 负责"是不是按我的方式做"。  
> 中间靠后台连接串起来。

早期版本中曾使用"能力层、记忆层、调度层"的三层结构。发布稿仍保留了这个逻辑，但改成了更口语化的表达。

这样既保留了判断深度，又避免读者被架构术语压住。

---

### 06 三个人的早晨

这是发布稿最重要的场景段落。

三个场景分别对应三类高上下文工作：

1. 写作者：账号风格和历史选题。
2. 销售：客户关系和承诺边界。
3. 创业者：决策脉络和组织记忆。

这三个例子共同说明：

> 本地 Agent 不是替你从零生成内容，而是帮你从自己的历史上下文出发，再去调用平台能力。

这也是全文从"观点"落到"验证"的关键部分。

---

### 07 结尾

结尾回到标题：

> 未来你不是只有一个 AI 助手。  
> 你会有一个懂你的人，带着一群会干活的 Agent。

最后一句完成收束：

> 平台负责能力。本地 Agent 负责上下文。真正的智能，发生在两者之间。

这句话是发布稿最终判断的最短表达。

## 04 核心概念演进

### 从"个人 Agent"到"本地 Agent"

最初使用"个人 Agent"，是因为想强调它属于个人、服务个人、承载个人记忆。

但在公众号语境里，"个人 Agent"容易被误解为某个平台里的自定义助手。它没有天然解释"数据边界""本地资料""长期上下文"的含义。

"本地 Agent"虽然也不是完美概念，但更符合大众语义。它天然让读者想到：

- 更靠近自己的设备。
- 更靠近自己的资料。
- 更可控。
- 更不依赖单一平台。
- 更能保存自己的长期工作流。

最终发布稿选择"本地 Agent"，是为了牺牲一点技术精确性，换取更高的读者理解效率。

---

### 从"Coze 3.0"到"平台型 Agent"

早期版本反复写 Coze 3.0，是为了确保产品观察有现实依据。

但发布稿不适合把 Coze 3.0 写成唯一主角。因为文章真正要判断的是一类产品形态，而不是一个产品版本。

因此最终采用了"平台型 Agent"这个概念。

Coze 3.0、WorkBuddy、Dumate 都成为观察样本，它们共同指向"云端 Agent 团队"这个趋势。

这个调整让文章从产品评论升级为趋势判断。

---

### 从"记忆层 / 调度层 / 能力层"到"能力 / 上下文 / 后台连接"

早期的三层结构是：

- 平台是能力层。
- 个人 Agent 是记忆层和调度层。
- MCP / CLI 是连接层。

这个结构准确，但术语过多。

发布稿改成：

- 平台型 Agent 负责"能不能做"。
- 本地 Agent 负责"是不是按我的方式做"。
- 中间靠后台连接串起来。

这不是逻辑变浅，而是表达变轻。

公众号读者不一定需要记住架构图，但需要记住判断：

> 平台把事情做出来，本地 Agent 让事情变成"我的"。

## 05 写作策略变化

### 1. 从解释完整到判断清楚

V1.2 的优点是解释完整，但缺点是读者负担重。

V1.3 的目标不是让读者理解所有技术细节，而是让读者记住一个判断。

因此发布稿删掉了大量细枝末节，把更多篇幅留给核心判断和场景验证。

---

### 2. 从技术词到生活词

原来的表达包括：

- MCP
- CLI
- workflow
- 自托管
- 本地部署
- 调度层
- 能力层
- 长期记忆机制

发布稿尽量改成：

- 接工具
- 设权限
- 调流程
- 后台连接
- 调用平台能力
- 记得你的偏好
- 知道哪些信息不能乱发

这使文章更像写给普通读者，而不是写给 AI 工具圈。

---

### 3. 从产品分析到意见表达

发布稿明确强化作者的观察、判断和预期。

例如：

> 最近看了几个大厂的云端 Agent 产品。  
> 这是好事。  
> 我的答案是：需要。  
> 所以我现在更关心的，不是……而是……  
> 这才是本地 Agent 真正可能变大的原因。

这些句式让文章呈现出"意见型文章"的主体感，而不是单纯在客观介绍产品。

---

### 4. 用场景完成验证

发布稿没有把"实际工作成果验证"写成方法论，而是藏在三个工作场景里。

写作者场景验证的是：本地 Agent 能延续账号风格和历史判断。

销售场景验证的是：本地 Agent 能避免平台方案脱离客户关系上下文。

创业者场景验证的是：本地 Agent 能维护组织决策连续性。

这三个场景让读者看到：本地 Agent 的价值不是抽象概念，而是可以发生在真实工作中的效率变化。

---

## 06 发布稿的核心判断

发布稿最终形成了以下几个判断。

### 判断一：平台型 Agent 会吃掉大多数通用任务

这不是坏事，而是 AI 普及的必要路径。

平台型 Agent 通过开箱即用、技能模板、云端能力和多 Agent 协作，把普通任务做到 70 分。对大多数人来说，这已经足够。

---

### 判断二：高上下文工作仍然需要本地 Agent

一旦任务涉及个人风格、客户关系、历史决策、隐私边界，平台型 Agent 的通用能力就不够了。

这类工作需要一个更懂用户历史和偏好的入口。

---

### 判断三：本地 Agent 不应该复制平台能力

本地 Agent 不需要比平台会更多事。它的核心价值是：

> 把平台的能力，变成你的能力。

它负责判断、筛选、保护边界、整合输出，而不是亲自完成所有任务。

---

### 判断四：配置必须消失

本地 Agent 如果要求普通用户学习复杂配置，就很难进入大众市场。

真正的产品趋势不是让用户懂更多技术，而是把复杂连接藏到后台，让用户只表达目标。

---

### 判断五：未来是"本地 Agent + 平台型 Agent"的协作

最终形态不是二选一。

平台型 Agent 提供能力，本地 Agent 提供上下文。一个负责干活，一个负责判断怎么为你干活。

## 07 与长文 Contract 的对应

### LF-1：活人感

发布稿通过"三个人的早晨"完成活人感建设。

陈、林、周不是抽象用户，而是具体工作中的人。他们有自己的场景、压力和上下文：

- 陈断更一年后复更，需要找回写作状态。

这些细节让文章从概念判断落到真实工作画面。

文章的内在问题是：

- 需要，但不是因为本地 Agent 更强。
- 平台负责通用任务，这是好事。

- 平台型 Agent

并通过一句话建立区分：

> 本地 Agent 的优势是：它知道你的事。

这个锚点足够清晰，适合公众号传播。

## 09 可复用经验

### 经验一：产品观察要尽快升级为公共判断

如果文章停留在"某产品发布了哪些功能"，读者只会把它当作产品资讯。

更好的写法是从产品里提炼趋势：

> 这个产品变化说明了什么？  
> 它改变了哪类人的工作方式？  
> 它让哪个旧问题变得更清楚？

本篇从 Coze 3.0 出发，但最终写的是平台型 Agent 与本地 Agent 的新分工，这是一次有效升级。

---

### 经验二：术语准确不等于表达有效

MCP、CLI、workflow 等词在技术上准确，但对公众号读者来说可能形成阻力。

发布稿把这些词翻译成"接工具、设权限、调流程、后台连接"，没有损失核心意思，却显著降低了阅读门槛。

面向普通读者的意见文，应该优先选择"读者能立刻感到和自己有关"的词。

---

### 经验三：概念需要一句能传播的话

本文最终能够成立，很大程度上依赖这组对照：

> 平台型 Agent 的优势是：它会很多事。  
> 本地 Agent 的优势是：它知道你的事。

这句话承担了概念锚定、传播记忆点和全文结构提示三重功能。

以后写类似文章时，应该尽早锚定一句能被记住和传播的判断。

---

### 经验四：活人感比完整度更重要

在有限篇幅下，保留三个具体人物的日常场景，比展开所有技术细节更有效。

读者更容易记住"陈写文章前查历史选题"，而不是"本地 Agent 通过 MCP 接入行业检索能力"。

---

### 经验五：从 Builder 视角转向 User 视角需要调整多个维度

这不只是改词汇，而是系统性改变：

- 开篇速度（快进核心问题）
- 概念表述（生活化而非技术化）
- 案例选择（日常工作而非产品功能）
- 论证方式（从"为什么 builder 需要"转向"为什么用户需要"）

一旦确定了目标读者，需要在这些维度上全面对齐。
