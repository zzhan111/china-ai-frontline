## 一、本篇工作流固化：产品观察如何变成意见型文章

005 跑通的是一条不同于 004 人物访谈的工作流。

004 的关键是把"讲述"改成"目击"，靠人物、场景、对白和白描让读者看见一个人。005 的关键是把"产品功能"改成"趋势判断"，靠概念锚定、判断推进和场景验证，让读者带走一个观点。

| 步骤 | 做什么 | 主导 | 沉淀物 |
|---|---|---|---|
| 1 产品观察 | 从 Coze 3.0 等平台型 Agent 产品中识别趋势信号 | 人定问题 + AI 整理 | `inbox/2026-06.md` |
| 2 初稿铺满 | 将产品观察扩展为长文，建立平台 / 个人 Agent 分工框架 | AI | `005-draft-v1.md` |
| 3 补事实 | 补充 Coze 3.0 客观信息，增强产品观察依据 | AI 搜集 + 人裁决取舍 | `005-draft-v1.1.md` |
| 4 补概念 | 扩写个人 Agent 定义和使用场景，使其与平台型 Agent 对等 | AI 重写 + 人反馈 | `005-draft-v1.2.md` |
| 5 体裁转换 | 从产品分析长文改为意见型短文，降低术语密度 | 人定方向 + AI 压缩 | `005-draft-v1.3.md` |
| 6 发布存档 | 将微信公众号发布稿同步为 preview | 人发布 + AI 存档 | `preview.md` |

本篇的核心经验是：

> **产品观察不能停在"它有什么功能"，要继续追问"它让什么分工变得更清楚"。**

## 二、v1 → v1.3 编辑案例：从产品分析到意见表达

### v1 诊断：判断成立，但读者入口偏窄

v1 的基础判断是成立的：平台型 Agent 和个人 Agent 不是替代关系，而是能力层与记忆 / 调度层的关系。

但这个版本存在三个问题。

第一，开篇铺垫较长，核心判断出现偏晚。读者需要先读较多产品介绍，才能进入"为什么一个人还需要自己的 Agent"这个真正问题。

第二，builder 视角较重。文章反复讨论平台能力、工具连接、MCP、CLI、workflow 等内容，更像写给 AI 产品从业者，而不是写给普通公众号读者。

第三，"个人 Agent"概念不够大众化。它容易被理解为"我在某个平台里创建的私人 bot"，而不是更靠近用户资料、工作流和隐私边界的长期上下文入口。

---

### v1.1 诊断：产品事实扎实，但 Coze 3.0 过于突出

v1.1 通过补充 Coze 3.0 的客观信息，让文章的观察基础更扎实。

这一版明确写出了 Coze 3.0 的产品方向：

- 从单 bot 转向 AI 团队。
- 从单次对话转向项目空间。
- 从单 Agent 执行转向多 Agent 协作。
- 同时服务新手用户和开发者用户。

但问题也随之出现：Coze 3.0 被写得太像全文主角。

这会让文章变成单一产品评论，而不是关于一类趋势的意见文章。后续版本因此做了一个关键调整：**Coze 3.0 只保留为观察入口，后文统一用"平台型 Agent"指代这一类大厂云端 Agent 产品。**

---

### v1.2 诊断：概念补足，但篇幅和术语过重

v1.2 最大的价值，是补足了"个人 Agent"的定义和场景。

这一版解释了个人 Agent 的几个特征：

- 跑在用户可控制的环境中。
- 能接触用户自己的草稿、文档、客户记录和会议纪要。
- 拥有长期记忆。
- 能调用外部平台能力。
- 不复制平台广度，而是作为记忆层和调度层存在。

它还扩写了三个场景：写作者、销售、创业者。

这些场景让文章开始有"活人感"。读者不再只是在读概念，而能看见这些 Agent 如何进入真实工作流。

但 v1.2 的问题是篇幅过长，技术解释仍然太多。MCP、CLI、自托管、workflow 等词虽然准确，但对目标读者会形成阅读负担。

---

### v1.3 定稿方向：压缩为意见型文章

v1.3 不是继续补充，而是做减法。

这一版做了四个关键编辑决策：

| 编辑决策 | 原因 | 结果 |
|---|---|---|
| "个人 Agent"改为"本地 Agent" | "个人 Agent"抽象，容易误解为平台 bot | 读者更容易理解它与资料、工作流、隐私边界的关系 |
| "Coze 3.0"降级为案例 | 避免文章变成单一产品评论 | 文章讨论对象升级为"平台型 Agent" |
| 弱化 MCP / CLI / workflow | 避免读者被术语劝退 | 改用"接工具、设权限、调流程、后台连接"等生活化表达 |
| 保留"三个人的早晨" | 场景是全文最有画面感的部分 | 用写作者、销售、创业者验证核心判断 |

v1.3 最终确立了文章的意见型表达方式：

> 平台型 Agent 的优势是：它会很多事。  
> 本地 Agent 的优势是：它知道你的事。

## 三、发布稿结构

发布稿采用 7 个部分。

### 开头：平台型 Agent 正在变成"云端团队"

开头从 Coze 3.0、WorkBuddy、Dumate 等大厂云端 Agent 产品切入，但不展开产品功能细节，而是直接提出趋势判断：

> 平台型 Agent 正在变成"云端团队"。

它们不再只是聊天框，而是在拆任务、调工具、交付结果。用户不再一个个操作工具，而是发出目标。

---

### 01 什么是本地 Agent

这一节建立全文的核心概念。

本地 Agent 不是某个平台上的 bot。它的核心不在"在哪里创建"，而在：

- 属于谁。
- 跑在哪里。
- 记得什么。

发布稿把本地 Agent 定义为一个更懂用户的工作入口。它可以读用户的草稿、文档、客户记录和会议纪要，也可以在调用外部能力前判断哪些信息能传出去、哪些只能留在本地。

---

### 02 平台会吃掉大多数通用任务，这是好事

这一节明确文章不是"反平台"叙事。

平台型 Agent 会吃掉很多通用需求：邮件、纪要、海报、小红书文案、竞品分析、周报。

这不是坏事。它说明 AI 正在从 demo 变成基础设施。

这节的关键判断是：

> 平台型 Agent 该赢。如果平台不赢，说明 AI 还没进入普通人的日常工作。如果平台赢了，说明 AI 终于从 demo 变成了基础设施。

---

### 03 但有些工作，差的就是那 20 分

这一节完成价值拐点。

平台能把很多通用任务做到 70 分，但有些任务 70 分就是不够：

- 一篇要代表账号风格的文章。
- 一封要发给关键客户的邮件。
- 一次会影响产品路线的会议总结。

这些任务不只取决于 AI 会不会做，而取决于 AI 了不了解用户。

---

### 04 配置不该是用户的工作

这一节回应本地 Agent 最大的产品难题：普通用户不想配置。

早期版本写的是 MCP、CLI、workflow，发布稿改成更贴近日常语言：

> 整理资料，接工具，设权限，调流程。

这节的关键判断是：

> 不是让更多人学会配置，而是让配置消失在一个懂你的助手后面。

---

### 05 新的分工

这一节将全文判断压缩为清晰分工：

> 平台型 Agent 负责"能不能做"。  
> 本地 Agent 负责"是不是按我的方式做"。  
> 中间靠后台连接串起来。

这是早期"能力层 / 记忆层 / 调度层"三层框架的白话版。

---

### 06 三个人的早晨

这是发布稿的场景验证段落，也是本文最重要的可读性来源。

三个场景分别对应三类高上下文工作：

- 写作者：账号风格、历史选题、表达偏好。
- 销售：客户关系、承诺边界、沟通上下文。
- 创业者：历史决策、会议脉络、组织记忆。

这三个场景证明同一件事：

> 本地 Agent 不是替代平台干活，而是带着你的上下文，去调用平台能力。

---

### 07 结尾

结尾回到标题：

> 未来你不是只有一个 AI 助手。  
> 你会有一个懂你的人，带着一群会干活的 Agent。

最后一句完成全文收束：

> 平台负责能力。本地 Agent 负责上下文。真正的智能，发生在两者之间。

---

## 四、关键概念决策

### 1. 为什么用"本地 Agent"而不是"个人 Agent"

"个人 Agent"强调属于个人，但语义偏抽象，容易让读者理解成平台里的自定义 bot。

"本地 Agent"更符合大众直觉。它天然暗示：

- 更靠近用户自己的资料。
- 更靠近用户自己的工作流。
- 更可控。
- 更重视隐私边界。
- 更能保存长期上下文。

发布稿也避免把"本地"写窄，明确它不一定只跑在电脑本机上，也可以跑在私有服务器、NAS 或其他用户可控制的环境里。

---

### 2. 为什么弱化 Coze 3.0

Coze 3.0 是重要观察入口，但不是文章主角。

文章真正要写的是一类趋势：平台型 Agent 正在从聊天工具变成云端团队。

因此发布稿只在开头点名 Coze 3.0、WorkBuddy、Dumate，后文统一使用"平台型 Agent"。

这样文章从产品评论升级成趋势判断。

---

### 3. 为什么删掉大量技术词

早期版本中，MCP、CLI、workflow、自托管等词有助于准确解释 Agent 架构，但会让普通读者产生距离感。

发布稿保留背后的逻辑，但换成更轻的表达：

| 技术表达 | 发布稿表达 |
|---|---|
| MCP / CLI | 后台连接、调用外部能力 |
| workflow | 调流程 |
| 自托管 / 本地部署 | 跑在用户能控制的环境里 |
| 记忆层 / 调度层 | 记得你、替你判断怎么做 |
| 能力层 | 会干活的平台能力 |

这次编辑的原则是：**不是降低判断深度，而是降低读者进入成本。**

---

### LF-6：场景调性

本篇不是宏大技术叙事，而是日常工作流叙事。

## 六、本稿沉淀的方法论

### 方法一：产品观察要升级成公共判断

产品文章不能停在"某产品发布了什么功能"。

更值得写的是：

> 这个产品变化说明了什么？  
> 它让哪种旧分工失效？  
> 它让哪种新分工变清楚？

本篇从 Coze 3.0 出发，但最终写的是平台型 Agent 和本地 Agent 的新分工。

---

### 方法二：意见型文章要有一句能被带走的话

本文最终能成立，依赖这组对照：

> 平台型 Agent 的优势是：它会很多事。  
> 本地 Agent 的优势是：它知道你的事。

这句话同时承担三个功能：

- 概念解释。
- 文章主线。
- 传播记忆点。

---

### 方法三：复杂技术要翻译成生活负担

早期版本讨论的是 MCP、CLI、workflow。发布稿讨论的是整理资料、接工具、设权限、调流程。

这不是把技术讲浅，而是把技术问题翻译成用户问题。

读者不关心协议本身，读者关心的是：

> 我是不是又要为了用一个工具，先学一堆东西？

### 方法四：场景不是例子，而是验证

"三个人的早晨"不是为了举例凑篇幅，而是为了验证全文判断。

写作者、销售、创业者分别证明：

- 本地 Agent 能延续表达风格。
- 本地 Agent 能维护客户关系上下文。
- 本地 Agent 能保存组织决策脉络。

这些场景让"本地 Agent 负责上下文"不再是抽象判断。
