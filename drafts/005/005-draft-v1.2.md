平台 Agent 的优势是：它会很多事。

个人 Agent 的优势是：它知道你的事。

这两句话，是 Coze 3.0 之后理解 Agent 生态最重要的一条分界线。

如果你在海外，只是偶尔听到扣子、Coze、豆包这些名字，很容易把它们归类成"中国版 GPTs"或者"另一个低代码 Agent 平台"。

但 Coze 3.0 在做的事情，比这更进一步。

打开扣子官网，首页展示的不是一个聊天框。而是一个叫"产品发布筹备"的项目。

项目里有一个用户，和五个 Agent。

用户林 Mia 输入了一句话："我们需要为官网设计一个首屏的产品宣传片。"

扣子 Agent 立刻把任务拆成四步：创作 Agent 撰写脚本，法务 Agent 审查合规风险，视频 Agent 生成 4K 素材，编程 Agent 把新版视频部署上线。每一步都有独立的 Agent 在推进，它们在同一个项目空间里传文件、同步上下文、互相交接。

几分钟后，扣子 Agent 在对话框里汇报："本次任务已全部闭环。物料清单和发版 Checklist 已整理，请查收。" [Coze](https://www.coze.cn/)

这是一个重要的产品信号。

Coze 3.0 不再只让你"创建一个会聊天的 bot"。它让你在一个项目里召集一组 Agent，它们各司其职、互相交接、持续推进。用户不再是每一件事的执行者，而更像一个在中间调度的项目经理。

更有意思的是，它不只在做云端。

在官网的"你的 Agent，你来定义"区域，Coze 3.0 展示了三款可接入的本地 / 自托管 Agent：Claude Code、Codex CLI、Openclaw。旁边标注着"local / self-hosted"。

面向开发者，它强调 CLI 与 MCP 集成，可以"一次编排多个 Agent，无需切换终端"。

面向新手，它又说："无需配 API 或理解 MCP，一键安装客户端就能拥有满配伙伴。" [Coze](https://www.coze.cn/)

它在同时吃两端。

一端是不想配置、不想学工具、只想打开就用的普通用户。一端是有本地工具、命令行、私有工作流、长期上下文的深度用户。

也正是因为它同时吃两端，Coze 3.0 提出了一个大问题。

问题不是"大厂会不会吃掉所有 Agent 创业公司"。

那个问题太小了。

真正的问题是：

当平台已经把模型、技能、项目空间、长期记忆、云端算力、本地工具接入、CLI 和 MCP 全部打包好，一个普通人还需要一个"自己的"个人 Agent 吗？

我的答案是：需要。

但原因不是个人 Agent 会比平台会更多事。

恰恰相反。个人 Agent 不应该和平台比"会多少事"。

平台一定更全，模板一定更多，专用 Agent 一定更丰富，云端算力一定更便宜。

个人 Agent 的价值在另一层。

它不是替代平台能力。

而是带着对"你"的理解，去调用平台能力。

---

## 一、什么是个人 Agent

Coze 3.0 是平台 Agent 的代表。但反过来，个人 Agent 到底是什么？

它不是你在某一个平台上创建的 bot。不是你在 Coze 上配置的一个"写作助手"。不是你在 ChatGPT 里开的一个自定义 GPT。不是你在 Dify 上搭的一条工作流。

个人 Agent 的核心特征不是"在哪里创建"，而是"属于谁、跑在哪里、记得什么、不把什么交出去"。

### 它住在你自己的机器上

一个典型的个人 Agent，不运行在平台服务器上。

它跑在你的笔记本电脑、你的 NAS、你租的一台云服务器，或者一台一直开机的迷你主机上。它的运行环境是你自己控制的。你可以随时关掉它，可以看它的日志，可以知道它什么时候调了什么工具、读了什么文件、把什么内容发到了哪里。

这不是技术洁癖。

这是一个很实际的问题：当你让 AI 处理工作邮件、客户记录、合同条款、产品路线讨论、投资人沟通，你不可能每次都把这些内容上传到一个你无法控制的平台。

平台有平台的隐私政策。但隐私政策和隐私控制是两回事。

隐私政策告诉你"我们会怎么用你的数据"。隐私控制意味着你自己决定数据能不能出你的机器。

个人 Agent 的底线是：数据可以不离开你的环境。

它能读你本地的文件夹，但不把文件上传到云端。它能检索你的笔记、邮件、聊天记录，但所有索引都存在本地。它可以在你需要的时候调用平台的云端能力——比如生成一段视频、做一轮联网搜索——但调用之前它会让你确认：哪些信息可以传出去，哪些不能。

### 它不是一次性的对话，它有长期记忆

平台 Agent 最大的限制不是能力，是记忆。

你在 Coze 上打开一个项目，Agent 在这个项目里记得上下文。但你把 Coze 关了，下一次打开一个新项目，一切从头开始。

你在 ChatGPT 里聊了一百轮，它有时候能跨对话记住你的一些偏好——但那个记忆是黑箱。你不知道它存了什么，不知道怎么修改，不知道怎么删除。你只能相信它没有记错。

个人 Agent 的长期记忆是透明的。

它把和你有关的信息存成一个你可以查看、修改、删除的知识库。你上次给客户 A 的报价是多少，你三个月前为什么否掉了一个选题，你的文章里从不用哪些词，你的产品路线里有哪些被砍掉的方向、为什么砍——这些东西不是藏在模型参数里的一堆概率，而是你可以在本地打开、编辑、搜索的结构化记录。

这意味着两件事。

第一，你不需要每开一次新对话就重新告诉 AI 你是谁。个人 Agent 在对话开始之前就已经知道你是谁。你不是在每一次 prompt 里解释自己的身份，而是在长期维护一个关于"你"的上下文。

第二，记忆是可迁移的。如果一个个人 Agent 的底层模型换了，记忆还在。如果你换了一台机器，记忆可以带过去。如果一个工具不再好用了，记忆不受影响。你不被任何平台锁定，因为关于你的信息不归平台所有。

### 它接 MCP 和 CLI，不是因为它高级，而是因为它不需要把所有能力都自己做

个人 Agent 不需要自己会写代码、会做 PPT、会生成视频、会分析表格。

它会通过 MCP 和 CLI 去调用别人做这些事。

MCP，Model Context Protocol，是一个让 AI 可以调用外部工具的开放协议。你可以把它理解成 AI 世界的 USB 接口。一个工具只要支持 MCP，你的个人 Agent 就能接上它：本地文件系统、浏览器、笔记应用、日历、邮件客户端、代码仓库、数据库，甚至另一个 Agent。

CLI，命令行接口，让个人 Agent 可以在不离开终端的情况下执行操作：运行脚本、调用 API、创建文件、打包数据、触发部署。

这些东西对普通用户来说听起来很技术。但关键在于：**接这些工具的是 Agent，不是你。**

你的个人 Agent 在后台通过 MCP 接上了你的文件系统、笔记、日历、邮件。它通过 CLI 调用了平台上的专业 Agent。你不需要知道 MCP 是怎么配置的，就像你不需要知道你的手机是怎么管理内存的。

你只需要告诉个人 Agent：帮我做这件事。

它自己去判断该调谁的 API、该读哪个文件、该叫哪个专业 Agent 出来干活。

### 它不是一个工具，它是一个入口

聊到这里，个人 Agent 的轮廓已经很清楚了。

它不是平台上一个配置好的 bot，而是你本地或私有环境里一直跑着的一个 AI 进程。

它不是每次对话重新认识你的通用助手，而是一个长期积累关于你的知识、偏好和历史的私人工作台。

它不是试图把一百种能力都装在自己身上，而是通过 MCP 和 CLI，把平台上的专业 Agent、本地工具、云端服务串成一条为你定制的工作流。

它不要求你把数据交给平台。它让你自己决定：什么留在本地，什么可以调出去，什么永远不出你的机器。

最后，也最重要的是：它不是一个你要"学"的工具。

工具是你打开它、用它、关掉它。

个人 Agent 的目标，是变成你工作流里一个不需要打开的东西。它一直在那里，等着你告诉它下一件事。

## 二、平台会吃掉 70-80% 的任务，而且这是好事

先承认一件事：平台 Agent 会吃掉很多需求。

一封普通商务邮件。一份会议纪要。一段小红书文案。一张活动海报。一个客服 FAQ。一次轻量竞品分析。一份周报。一段短视频脚本。

这些任务，一个现成的平台 skill 就能做到 70 分。

对大多数人来说，70 分已经够了。

不值得为了从 70 分做到 90 分，花三个小时去配置工作流、整理文件、训练偏好、接 MCP、调 CLI、维护长期记忆。

这不是用户不专业。

这是非常理性的取舍。

一个运营每周要写三份复盘。她需要的不是"完美符合个人风格的叙事"，而是"省下开头那四十分钟"。一个 70 分的平台模板就能做到这件事。

一个客服主管要统一 FAQ。她需要的不是"了解每个客服的个人风格"，而是"把散落在聊天记录里的高频问题快速归纳成可用的回答"。平台 Agent 做这件事比人工快十倍。

一个创业者要做竞品分析。他需要的不是"深度依赖我个人判断的洞察框架"，而是"让我先看到结构，我再加上我的判断"。平台 Agent 正好承担"结构"的那一半。

这些需求，平台该赢。

如果平台不赢，说明 Agent 还没进入普通人的日常工作。如果平台赢了，说明 Agent 终于从技术 demo 变成了基础设施。

所以"平台吃掉通用任务"不是一个悲观的判断。

它是一个必然的、让更多人用上 Agent 的过程。

## 三、但有些工作，70 分就是不及格

问题在于，人的工作不只有通用任务。

一篇要代表你个人账号风格的文章，不是"结构完整"就够。

一份要发给关键客户的报价方案，不是"语气礼貌"就够。

一次会影响产品路线的用户访谈总结，不是"提取要点"就够。

一份给投资人的更新邮件，不是"写得专业"就够。

这些工作的共同特征是：它们的结果不取决于 AI 会不会做这件事，而取决于 AI 了不了解做这件事的"你"。

一个内容创作者打开平台 Agent，让它写一篇文章。平台能写。结构不错，标题清楚，段落也有节奏。

但他读完会觉得不对。

不是因为写得差，而是因为不像自己。

平台不知道这个账号过去写过什么，哪些观点已经反复说过，哪些选题被否掉过，哪些读者反馈曾经改变过这个号的方向。它不知道这个作者讨厌"赋能""闭环""重塑"这类词。它不知道这篇稿要发在一个断更一年、正在冷启动复更的号上，不能一上来就写得太宏大。

它能写文章。

但不能延续一个账号。

一个销售让平台 Agent 写一封客户跟进邮件。

邮件本身可能不错。礼貌、完整、有行动号召。

但真正决定这封邮件能不能发出去的，是很多没有写在 prompt 里的信息：这个客户上次为什么犹豫，预算真正卡在哪里，谁才是决策人，哪句话以前提过客户很反感，哪项承诺销售自己还没跟产品团队确认。

平台能生成邮件。

但不能理解一段客户关系是怎么走到今天的。

一个创业者让 AI 总结一场会议。

纪要很容易生成。谁说了什么，决定了什么，下周要做什么，AI 都能整理出来。

但创业者真正需要的不是一份纪要。

他需要的是一个知道公司正在往哪里走的助手。它要知道这家公司上个月为什么砍掉一个方向，哪个投资人的反馈曾经让产品路线转弯，哪些用户访谈的结论已反复出现三次，本周最重要的不是加功能而是把已有功能做稳定。它还要知道，会议里哪些话只是情绪发泄，哪些才是下一步真正要进入执行的决定。

平台能总结会议。

但不能维持连续决策。

这些场景说明了同一件事。

平台 Agent 的优势，是它见过很多任务。

个人 Agent 的优势，是它见过"你"的很多任务。

一个是广度。一个是连续性。

70 分工具和 90 分工具的差距，在这里不再是润色差距，而是竞争力差距。

## 四、个人 Agent 真正的对手不是 Coze，是用户懒得配置

写完上面这一节，可能会让人产生一个印象：个人 Agent 是给"愿意为工作花时间的人"用的。

这个印象没有错，但它只说了一半。

个人 Agent 真正的对手不是 Coze，不是豆包，不是飞书，不是 ChatGPT，不是任何一个大厂平台。

它真正的对手是用户懒得配置。

大多数用户不想整理文件。不想授权工具。不想接 MCP。不想写 workflow。不想告诉 AI 自己的写作偏好、客户关系、项目历史和隐私边界。

他们只想打开就能用。

一个平台 skill 如果是 70 分，他们会选 70 分。

一个个人 Agent 即使能做到 90 分，如果要求他们先花三个小时输入上下文、整理资料、设置偏好、接入工具链，他们会说：算了，70 分够了。

这不是一个技术问题。

这是一个使用意愿问题。

大多数任务不值得深度个性化。大多数用户没有动力维护工作流。大多数人对 AI 的期待是"帮我省时间"，而不是"给你我的时间，你以后可以更好地帮我省时间"。

所以，个人 Agent 不会是全民产品。

至少现在不是。

它最早服务的人，一定是那些"不配置会死"的人。

内容创作者每天要写。如果不整理素材、不维护选题库、不让 AI 记住自己的表达偏好和历史文章，每次写都是从零开始，时间一长会崩溃。

销售每天要跟客户。如果不记录每次沟通结果、不维护客户上下文、不让 AI 知道哪些信息是关键决策变量，越做越累，丢单率也会上去。

创业者每天要做决策。如果不沉淀会议记录、项目复盘、投资人反馈、用户访谈、产品路线变更日志，几个月后连自己当初为什么这样决定都不一定记得清楚。

对这些人来说，配置不是额外负担。

配置是基础设施建设。

前期花三个小时，是为了接下来半年每天节省四十分钟。

但——

如果文章只停在这里，个人 Agent 仍然只是一小群深度用户的小众工具。

真正让这件事变得更大的，是另一层变化。

## 五、个人 Agent 不该让所有人学会配置，它应该让配置消失

过去半年，如果你关注 AI 工具圈，你会反复看到一个词：MCP。

Model Context Protocol。一个让 AI 可以调用外部工具、读取文件、连接服务的开放协议。

还有一个词：CLI。命令行接口。让开发者不离开终端就能调度 Agent。

对于技术人员，这两个词是基础设施。

对于普通人，这两个词是门槛。

很多人一听到 MCP、CLI、workflow、API、本地部署、自托管，就已经划走了。

但 Coze 3.0 在产品上做了一件很聪明的事：它把 MCP 和 CLI 藏起来了。

对新手，它说"不需要配置 API 或理解 MCP，一键安装客户端就能拥有满配伙伴"。对开发者，它同时开放 CLI 与 MCP 集成。

这意味着同一套基础设施，被包装成了两种入口。

这件事对个人 Agent 的意义非常大。

因为它说明了一件事：**配置可以不是用户的工作。**

今天你需要手动配置 MCP、接 CLI、写 workflow、训练记忆、整理文件、设置权限。这些东西让个人 Agent 停留在极客群体里。

但未来，一个足够好的个人 Agent 会在后台完成这些事。

用户只需要告诉它目标。

它自己判断需要调用什么能力，自己通过 MCP 或 CLI 去接平台 skill、拉专业 Agent、读本地文件、查历史上下文，然后把结果整理成用户习惯的格式。

用户看到的是一句话：

"帮我按我的方式做完这件事。"

背后发生的是一整套调度。

这才是个人 Agent 走向大众用户的可能性。

不是让更多人学会配置。

而是让配置逐渐消失在一个懂你的 Agent 后面。

## 六、新的分工：平台是能力层，个人 Agent 是记忆层和调度层

到这里，我们可以重新画一张 Agent 的分工图。

过去讨论 Agent 生态，大家习惯的画法是横向的：

左边是平台 Agent，右边是个人 Agent。各有地盘，分层共存。

但 Coze 3.0 给出了一种更准确的画法。这张图应该是纵向的三层。

**上层：记忆层。个人 Agent。**

它知道你是谁。知道你在做什么。知道你的文件。知道你的偏好。知道你的客户。知道你的历史决策。知道你的隐私边界。知道哪些表达是你的声音，哪些不是。

**中层：调度层。MCP / CLI / 本地 Agent。**

它负责把记忆层的判断，转化成对能力层的调用。该叫哪个平台 skill，该用哪个专业 Agent，该读哪个本地文件，该在什么时候把结果吐回给用户。

**下层：能力层。平台 Agent。**

它负责提供生产能力。模型、算力、技能包、专业 Agent、行业模板、云电脑、云手机、代码执行环境、视频生成、数据分析、PPT、表格、网页开发。

三层各司其职。

平台负责"能做"。

记忆层负责"该为谁、怎么做"。

调度层负责把两者连在一起。

这个三层结构有一个很重要的推论：个人 Agent 不需要复制平台的能力。

它不需要自己建一个 skill store。

它不需要自己训练行业专家 Agent。

它不需要和平台比模板数量、比模型质量、比云端算力成本。

它只需要做好一件事：把平台的能力，变成"你的能力"。

平台能写文案。

个人 Agent 让它写出"你的文案"。

平台能生成方案。

个人 Agent 让它生成"对你这一个客户有效的方案"。

平台能总结会议。

个人 Agent 让它总结出"对你这个公司下一步决策有用的会议"。

这不只是"公共工具箱 + 私人工作台"的升级。

这是一个新角色：**你的项目负责人。**

公司里可以有很多外包团队和专业供应商，但你仍然需要一个真正懂你业务的项目负责人来决定用谁、怎么用、用完之后怎么整合成你的东西。

平台 Agent 是供应商。

个人 Agent 是你的项目负责人。

---

## 七、三个人的早晨：当个人 Agent 开始替你调度平台能力

判断写到这个程度，需要落到几个具体的人身上。

### 写作者

陈在做一个面向海外华人的中文科技账号。账号叫"跨境码农日记"，两万出头关注，不算大，但读者黏性很高——因为他写的不是资讯，而是"一个在柏林远程工作的中国开发者，怎么看硅谷和国内的产品变化"。

他断更过一年。原因是孩子出生。复更以后最大的问题不是没东西写，而是每次都要花很长时间重新进入写作状态。翻草稿、查旧文章、确认某个角度有没有写过——这些事情吃掉的时间比真正写作还多。

后来他把这些事交给了一个跑在他家里那台 Mac mini 上的个人 Agent。这台 Mac mini 一直不关机，Agent 就在上面常驻运行。它的配置很简单：只读陈的本地草稿文件夹、浏览器书签里的信源列表、过去发布文章的纯文本备份。禁止上传任何内容到云端。这是陈给自己定的底线——他的草稿和已发布内容可以在本地随便用，但不能上传到任何一个他无法控制的服务器。

这天早上，陈想写 Coze 3.0。

他只输入了一句："帮我对一下，Coze 3.0 这个选题能不能写。"

他的个人 Agent 在本地扫描了他的草稿文件夹和已发布文章。三秒后返回了两条信息：第一，三周前有一篇 inbox 笔记，标题是"Coze 3.0 直播观感"，里面有两个关键判断——"它在做 AI 团队而不是 AI bot"和"平台型 Agent 和个人 Agent 会分层共存"。第二，两个月前那篇教育 AI 出海的文章里有一段讨论了"平台产品和个人定制工具的分层逻辑"，角度和这次可以衔接。

Agent 接着说了一句："这两条素材说明选题方向不重复。建议用'平台越强，个人 Agent 的位置反而更清楚'做主线，和历史判断形成递进关系。"

陈决定写。

接下来，他的个人 Agent 开始调度外部能力。它通过 MCP 调了 Coze 3.0 扣子 Agent 的联网搜索，拉回了官网最新介绍、开发者文档要点和社区讨论热帖。又调了一个英文信源检索 Agent，扫了一圈海外对"multi-agent collaboration space"的讨论——OpenAI 的 Projects、Google 的 Agent 协议、Claude Code 的 MCP 生态，大致结构拉出来，给陈做对照分析的素材。

素材都回来了。

但不是直接能用。

扣子 Agent 返回的内容是平台风格：全面、清晰，带着产品文案的语气。英文检索 Agent 返回的内容是开发者社区风格：技术细节多，但上下文缺失。

陈的个人 Agent 做了最后一件事：它把所有素材过了一遍陈过去十篇文章的语言风格，标出了三处措辞和平台原文不一致的地方——"赋能"改成了"支持"，"闭环"改成了"完成"，一处关于中国市场的数据和英文信源有出入，标红让他亲自核查。

陈看完，开始写。不是从零写，而是从一个已经被"自己"整理过的起点开始写。

省下的不是写作时间。

省下的是进入写作状态之前，那段最容易放弃的准备工作。

### 销售

林在一家做跨境电商 SaaS 的公司做客户成功。公司不大，她一个人跟十几个企业客户。客户分布在深圳、杭州、广州和新加坡。

她的工具有很多：飞书有内部沟通和客户群，企业微信有另一批客户，CRM 里有正式记录，邮件里有报价历史和合同附件，会议纪要在飞书文档里散落各处。

过去她最累的不是见客户，而是见客户之前拼上下文。每次都要在四个工具之间来回切，把一段客户关系从碎片里重新拼出来。

后来她在自己的笔记本上跑了一个个人 Agent。Agent 被接进了飞书消息记录、企业微信存档和 CRM 系统的只读接口。所有数据都存在本地，不经过任何云端。

这天上午，她要见一个叫老周的客户。跟了四个月，还没签。

她输入："老周，今天下午见，帮我过一下。"

个人 Agent 从多个来源聚合出了当前状态：最近两次沟通里，老周提到预算审批延迟，财务那边在等 Q3 预算释放；产品团队两周前修了一个老周反馈过的库存同步 bug，但还没正式通知他；上次发的方案里 SLA 那一条，法务还没确认，林自己在 CRM 里标注了"此项暂不承诺"。

然后 Agent 开始调度平台能力。它调了 Coze 上的行业检索 skill，拉出了老周这个细分品类最近三个月的动态——有两家竞品在降价，有一家刚拿了融资，这些都是林之前没注意到的。又调了平台的表格生成 skill，把老周公司的需求和产品功能做了一版对照表，方便下午当面过。

平台返回的方案包是标准格式：结构完整，数据清晰，但语气是平台模板的通用商业风格。

林的个人 Agent 在交付前做了处理。文案里所有"行业领先"都改成了具体数字——林从来不用虚词，她的客户也不吃这套。SLA 条款处被标红，加上了她从 CRM 里同步过来的备注："此项需法务最终确认，暂不对客户承诺。"方案的优先级也被调整了：老周过去四次沟通里有三次主动提了响应速度的问题，个人 Agent 把"响应速度"提到了方案第一页，把"功能丰富度"往后放了。

林在去客户公司的地铁上看完，只改了一处——把 Agent 自动生成的一个数据换成了她自己上周和产品经理确认过的最新数字。

其它都没动。

### 创业者

周是创始人。公司做智能硬件出海，十五个人，产品刚过小批量验证，正在谈 A 轮。

公司不大，但信息密度很高。

用户访谈、投资人会议、供应链沟通、产品评审、团队周会。每周产生大量对话，大部分留在飞书聊天记录和会议纪要里，事后几乎没人回看。

周最怕的不是做决策，而是三个月后投资人问"你们上次是怎么想的"，他发现自己已经讲不清楚当时的逻辑了。

他的个人 Agent 跑在办公室里一台不关机的 Linux 工作站上。Agent 每周自动抓取飞书上的会议纪要和周的关键决策讨论，抽取出决策的背景、结论、依据和反对意见，结构化存进本地数据库。不分析，不推荐，只存档和关联。

这天早上，一个投资人在微信上问了一句："你们上一版砍掉那个离线语音功能的时候，有没有做过用户验证？"

周打开个人 Agent，输入那个功能的名字。

Agent 返回了一条完整的时间线。

三个月前，七月十四号的产品评审会上，CTO 提出了两条反对离线语音的理由：芯片功耗会超预算，同时东南亚市场的用户调研显示离线场景占比不到 5%。两天后，七月十六号的决策会上，团队一致同意砍掉。Agent 还从当时的会议纪要里摘出了一条备注——一位参与过早期测试的印尼用户的访谈记录，原文就一句话："没网的时候我才发现这个功能不存在，但我其实也不怎么用。"

周正要把这条发给投资人，Agent 补充了一条新信息：平台 Agent 两周前做的一轮用户调研里，有三位新用户以不同方式提到了离线场景的需求——方向不完全一样，更偏向本地存储而非离线语音，但可能值得重新放进产品 backlog 讨论。

周把完整上下文转发给了产品负责人。

他不是从聊天记录里翻出来的。

是一个一直记着的 Agent 帮他调出来的。

---

三个人的共同点是什么？

不是他们有技术背景。陈写内容，林做客户成功，周管公司。都不是开发者。

不是他们热爱配置。如果可以，他们都不想花时间摆弄工具。

而是他们的工作有一个共同特征：**结果质量高度依赖个人上下文，而上下文的维护成本正在变成瓶颈。**

过去这个瓶颈似乎无法突破。

因为平台工具天然不擅长长期记忆。平台每一次对话都在鼓励"重新来过"，因为长期记录每一个用户的独特上下文对平台来说成本太高、变现太难。

但现在，MCP、CLI、本地 Agent、自托管工具、平台 skill 可调用——这些不同的积木开始出现在同一张桌子上。

组装它们的方式，决定了 Agent 的真正分界线。

不在于"谁会更多事"。

而在于"谁带着你的上下文，去替你叫对的人来做这件事"。

---

## 八、结尾

Coze 3.0 是一个信号。

但它不是"大厂的 Agent 又更新了"那种信号。

它是另一种信号：Agent 生态开始长出分层结构。

平台 Agent 继续往前走。它们会让更多普通人第一次用上 Agent，让更多人从"听过 AI"变成"用过 AI"。它们的优势会越来越集中在广度、通用性、开箱即用和低成本调用上。

但平台每向前走一步，也会让另一件事变得更清楚。

当 AI 能力越来越平台化，个人工作流反而会变成新的稀缺资产。

平台知道你面前的任务。

只有你自己的个人 Agent 知道你上次停在哪里。

平台能调一百种能力。

只有你自己的个人 Agent 知道应该为你调哪一种、怎么调、调完之后怎么改成你的东西。

未来你不是只有一个 AI 助手。

你会有一个懂你的人，带着一群会干活的 Agent。

## 评注

v1.2 相比 v1.1 的核心变化：

**第一，新增了第二节《什么是个人 Agent》。** 这一节从五个维度详细定义了个人 Agent：它住在你自己的机器上（本地运行、数据主权）、它长期积累你的上下文（透明可管的长期记忆）、它通过 MCP 和 CLI 调度外部能力（不复制平台、只连接平台）、它不是工具而是入口。每个维度都给出了具体的形态描述和与平台 Agent 的对比，与第一节 Coze 3.0 的详细介绍形成了对等篇幅。

**第二，人物场景增加了"活人感"细节。** 陈不再只是"内容创作者"，而是"在柏林远程工作的中国开发者，账号两万关注，断更原因是孩子出生"。林不再只是"销售"，而是"用飞书、企微、CRM、邮件四个工具拼上下文的客户成功"。周的公司有了具体方向（智能硬件出海、A 轮），Agent 跑在"办公室里一台不关机的 Linux 工作站"上。这些细节按 LF-1（活人感）的要求，让读者不是在看三个类型化角色，而是在看三个具体的人。

**第三，场景中个人 Agent 的运作机制被写得更具体。** 每个场景都展示了：个人 Agent 先读取本地上下文（草稿文件夹、CRM 只读接口、飞书会议纪要存档），再通过 MCP 调度平台能力（扣子 Agent 联网搜索、行业检索 skill、平台表格生成 skill），最后做个人化处理（语气适配、优先级调整、冲突标注）。这套工作流在三个场景中保持了一致性，让读者能清晰地看到"记忆层 → 调度层 → 能力层"的三层结构如何在实际工作中运转。

仍需注意的一个点：第二节《什么是个人 Agent》信息密度较高，偏向定义说明。如果后续迭代希望增加可读性，可以考虑把它和某一个具体人物的使用体验交织在一起写，而不是独立的说明章节。但当前结构的好处是清晰——读者可以先完整理解个人 Agent 是什么，再在场景中看到它如何运作。
