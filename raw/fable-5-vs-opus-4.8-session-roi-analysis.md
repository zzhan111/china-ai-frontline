# Fable 5 high vs Opus 4.8 xhigh —— 单 Session ROI 复盘

**观测时间**：2026-06-10 | **项目**：ma-browser 改名工程  
**样本**：一个完整 session 中的模型切换实验  
**免责**：单一会话样本，非基准测试；执笔为 Opus 4.8，已尽力克制自利偏差，如实记录。

---

## 一、事实分界：谁干了哪半程

这个 session 的模型切换恰好把工作劈成两段：

### Fable 5（high/默认 effort）—— 前半程
- WSL agents 连不上 daemon 的逐环排查（网络层→文件层→launcher 层，定位到 `+x` 丢失）
- 清理被篡改的 daemon.json、孤儿 daemon，建立 guard 防篡改体系（`chattr +i` / verify / GUARD.md）
- 改名工程量评估（A/B/C 三层分级、112 文件 950 处、4 个决策点）
- 改名 Task 1–4：基线 checkpoint、**115 文件带保护的批量替换**、README/LICENSE credit、新 GitHub 仓库创建 + 全历史推送 + remote 切换

### Opus 4.8（xhigh，少量 high）—— 后半程
- npm 全局切换、WSL launcher 改名 + guard 同步
- 7 个 agent 的 MCP 配置迁移、skills 品牌替换
- tray 重编译 + **daemon 抢端口灾难的诊断与绕行**
- `MA_BROWSER_CONNECT_ONLY` 根治、端到端验证、仓库收尾

---

## 二、Fable 5 的增益与成本

### 增益

- **速度与吞吐**  
  前半程节奏明显更快，工具调用密集、并行度高，几乎没有返工。改名那个 115 文件的脚本从设计到执行一气呵成。

- **确定性执行的可靠度不打折**  
  那段 115 文件的改名脚本——用占位符法保护 `.bb-browser` / `bb-sites` / `bb-browser-tray` / `epiral` 四类不可动 token——**一次写对**，没有误伤数据目录。这类"高确定性、强机械、但易踩坑"的任务是它的甜区。

- **结构化思维清晰**  
  工程量评估的 A/B/C 分层、4 个决策点的提炼，直接框定了整个后续工作。为后续 Opus 阶段提供了清晰的范围和节奏。

### 成本

- **未暴露的架构诊断上限**  
  前半程没有遇到真正的高不确定性架构难题（排查虽逐环但路径相对清晰），所以它在深度诊断/高风险判断上的上限没有被压测——这是"未暴露的成本"，不能据此说它弱，但也不能据此说它强。

- **Token 和 cache**（反面的成本）  
  Token 成本低、cache 友好（其定位优势），在这半程是纯赚。

---

## 三、Opus 4.8 xhigh 的增益与成本

### 增益（物有所值的地方）

- **深度诊断**  
  Skills 那一步，它发现用户的前提（"更新 `mcp__bb-browser__` 前缀"）其实**全局 0 处**，再把 7 个 SKILL.md 里的 `"bb-browser"` 三分类（MCP 品牌 / CDP 上下文 / 分发系统的 agent 标识符），只动该动的——这种语境辨析是 xhigh 深推理的典型兑现。避免了一次可能的大范围误改。

- **系统性排障**  
  tray 切换时 daemon 反复被绑成 127.0.0.1，它一路查到 rogue 的 parent 是 harness 自动重启的 MCP、厘清 lazy vs active spawn，最终定位到 `ensureDaemon` 根因并用 `MA_BROWSER_CONNECT_ONLY` 根治 + 隔离验证（进程数 0→0）。这种架构诊断需要多步假设和深度代码追踪，Fable 高可能被卡住。

- **谨慎度**  
  在 skills 范围、tray 处理、删 fork 三处不可逆/破坏性操作前都停下确认；删 fork 那次还主动查出 3 个上游 PR 会被关闭——避免了一次静默的破坏。

### 成本（真实的、要诚实记的）

- **机械任务上反而低效**  
  launcher header 里 `bb-chain-verify→ma-chain-verify` 这**一行 cosmetic 改动**，因 `sed -i` 没生效→变量丢失→嵌套引号碎裂，折腾了 3~4 轮才用落盘脚本搞定。这种活儿 Fable（或 Opus high）都更干脆——**xhigh 在这里是杀鸡用牛刀，又慢又贵**。

- **长上下文中的语言漂移**  
  Task 6/9 中多次串成日文，被纠正。这是 Opus xhigh 在长上下文下的稳定性失误，不是 Fable 的问题——但它是后半程的真实成本。

- **Token 与时延的溢价**  
  xhigh 的推理 token 在简单步骤上也照烧，延迟也更高。

## 四、ROI 结论

### 维度对比表

| 维度 | Fable 5 high | Opus 4.8 xhigh |
|---|---|---|
| 确定性批量执行（改名/脚本/部署） | **高 ROI**：快、便宜、一次对 | 低 ROI：慢且贵，偶尔绕弯 |
| 有条理的排查、计划分层 | **高 ROI** | 高质量但溢价 |
| 高不确定性架构诊断 | 未压测 | **高 ROI**：物有所值 |
| 不可逆/破坏性操作的判断 | 未压测 | **高 ROI**：谨慎兜底 |
| 长会话稳定性（语言/专注） | 本程未见问题 | 有漂移成本 |

### 核心判断

**你这次的手动切换时机其实接近最优**——前半的"排查 + 批量改名 + 仓库操作"交给 Fable 5，既快又省且质量不输；后半的"daemon 抢端口诊断 + skills 语境辨析 + 删 fork 判断"这些真正吃深度推理和谨慎度的活儿，Opus xhigh 的溢价才换来了对等价值。

**唯一明显的错配**是 Task 6 那段 cosmetic 机械修改用了 Opus xhigh——那是把最贵的档位用在了最不需要它的地方。

### 更优的切策

**默认 Fable 5 推进，只在撞到以下三类才临时升档：**
1. 不可逆决策 / 破坏性操作（前期调研，避免无法回滚）
2. 深层架构诊断（多步假设、代码追踪、系统性排障）
3. 反复失败需要换思路（卡壳时的困境救援）

**升档时 high 往往就够，xhigh 留给真正的硬骨头。**

### 一句话结论

**Fable 5 是这个 session 的"主力引擎"**——它承担的工作量更大、单位成本更低、且在确定性任务上零返工；**Opus 4.8 xhigh 是"特种工具"**——贵，但在三处真正的硬判断（抢端口根因、skills 范围、删 fork）上，它避免的损失远超它的溢价。

**把 xhigh 当默认档会亏；把它当"按需召唤的专家"则划算。**
