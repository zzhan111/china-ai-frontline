来源：screenpipe 项目调研 + 对 AI 路演生态的观察

用 screenpipe（开源桌面录屏+ASR，像是 AI 的眼和耳）无监督转录微信直播中的路演项目，为参赛选手提供结构化参考。

**screenpipe 核心能力**：
- GitHub 18.9k stars，YC S26（Mediar Inc.），MIT 开源，Rust+Tauri 桌面端（v2.4.280）
- 事件驱动截屏（app switch/click/typing/scroll）+ accessibility tree 提取（远优于全量 OCR），每帧配对截图+可访问树
- 本地 Whisper 实时语音转写 + 说话人识别（系统音频+麦克风双通道）
- SQLite FTS5 全文检索 + 语义搜索（embeddings），~300MB/8h 截图，5-10% CPU
- MCP server（AI 直接检索屏幕历史）、Pipes 插件系统（markdown 即 AI agent）
- 完全本地运行，无云依赖

**路演场景的独特价值**：
- 微信直播无 API 可调用，截屏+ASR 是唯一可行的全量采集方案
- 截屏获取 PPT 内容（技术架构、商业模式页）+ ASR 获取口头 pitch
- 选手经常错过同赛道对手路演 → 完整转录=完整竞争情报
- 可结构化导出：公司名/赛道/轮次/技术栈/商业模式/团队背景/投资人提问
- 进一步可做：按赛道聚类、相似项目指数、评委提问模式提取

**类似项目**：
- Rewind.ai/Limitless：商业闭源，macOS only，无插件系统
- Microsoft Recall：Windows only，隐私争议，无 ASR
- Granola/Otter.ai：纯音频转录，无屏幕上下文
- screenpipe 独特优势：端侧全量（屏+音），开源可定制管线，MCP 可被 agent 操作

**"眼+耳"读屏的扩展场景**：
- 线上路演/评审会 → 自动生成评审报告
- 竞品发布会直播 → 产品功能变化追踪
- 直播带货 → 话术策略逆向工程
- 网课/技术分享 → 自动笔记+代码片段提取
- 远程面试 → 结构化评估档案
- 任何「屏幕上有结构化信息+语音解释」的场景

## 2026-05-26 16:30

来源：微信群聊「AI 出海工具链」，讨论阿里国际站/京东/小红书 API 与 AI agent 接入

群里几个做跨境电商和独立站的，困境高度一致：AI 写文案、生图已经稳定了（亚马逊 listing 文案+主副图+详情页全链路跑通），但卡在"最后一公里"——没有 API 把内容推上去。

对话暴露了三个共识：
- **API 不平等**：硅谷公司（Twitter、Cloudflare、Google、Amazon SP-API）主动开放 API，中国平台（阿里国际站、1688、京东、小红书）封闭。不是技术问题，是信任问题——"万一你为非作歹怎么办"。
- **浏览器自动化是死胡同**：各家反爬机制不断升级，图形界面对大模型太绕，token 消耗大、不稳定。
- **终极愿景**是"文字 AI 组织，工作 AI 推"——agent 从生成到执行全链路闭环。

我的方案在群里引发了强烈兴趣：browse.sh（400+ 站点内部 API 端点集合）→ 翻译到 bb-browser 本地适配器 → 0 token CDP 调用。群里有人立刻去研究，有人要了我的 PR #79 链接。这说明痛点真实、方案有需求。

这其实是 **"API 不平等"时代的 agent 基础设施**：既然平台不给 API，agent 就通过浏览器自己"长"出 API。不是爬 HTML，是直接调到站点内部接口——和官方 API 等效，但不需要申请。

群里那个做亚马逊的已经能把 listing 生成跑稳，就差接 API 这步。shopify cli 在独立站已经把这条路走通了。接下来就是把亚马逊、淘宝、1688 也打通。

- 统计 browse.sh 中 e-commerce 类 skill 的数量和覆盖平台（amazon/ebay/shopify/etsy/1688 等），评估"电商全链路 agent"的覆盖率

来源：实际案例 — xx药业为线上统一价格，委托第三方开发跨平台价格监控系统

一个真实的 B 端需求案例：某药业品牌为了统一线上价格体系，请第三方公司开发了一套系统，专门监控各电商平台（京东、淘宝、拼多多等）上自家产品的售价，确保不低于约定价。

这背后是三个刚性需求：
- **价格监控**：实时扫描多平台 SKU 价格，低于红线自动告警
- **防止串货**：A 区的货出现在 B 区的店铺里，追踪货源链路
- **防止砸价**：下游经销商或同行恶意挂低价，损害品牌控价体系

这三个需求都高度依赖「跨平台数据采集」——但京东、淘宝、拼多多没有一家为此开放 API。

这和上一个 inbox 条目（API 不平等）高度共鸣：不只跨境电商有推内容的痛点，国内 B 端品牌方的控价需求同样被 API 封闭卡住。第三方公司目前大概率用爬虫或 RPA，反爬升级即失效，维护成本极高。

如果 bb-browser 适配器能覆盖淘宝/京东/拼多多的商品搜索 + 价格提取，这套系统可以被 agent 替代——定时扫描 → 价格对比 → 异常告警 → 自动生成报告。比「AI 推 listing」更靠近 B 端付费场景。

- 调研国内药企/品牌方的线上控价需求规模：有没有公开数据或行业报告？（搜索关键词：医药电商价格监控、品牌控价系统、渠道窜货管理）
- 评估 bb-browser 现有适配器对「价格监控」场景的覆盖率：淘宝、京东、拼多多已有适配器吗？还缺什么？
- 判断这个方向是否值得单独开一条内容支线（B 端品牌控价 vs C 端电商运营，受众不同）
