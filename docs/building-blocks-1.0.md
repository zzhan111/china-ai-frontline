# Building Blocks 1.0 — 从 009 全生命周期提炼的写作工程模式

> 来源：drafts/009/evolution.md（v1.0 → v1.1 → v1.1.1 → v1.2 → published）
> 五阶段全生命周期：research → topic card → drafting → quality → publishing
> 日期：2026-06-27

---

## 一、Research → Topic Card（调研到选题）

### 1.1 数据锚点先行

**规则**：每进入一个论点，先把数据摆在句首，再给判断。

**为什么**：读者（尤其是公众号读者）看到"$686.6M（同比+26%）"会在脑中先建立一个量级参考，然后再接受你的分析。反过来——"Xometry 增长非常快，2025 年营收 $686.6M"——读者会在前两个词就流失注意力。

**反例**：不要写"Xometry 的增长令人瞩目"，写"$686.6M（+26%）"。数字本身就是最好的形容词。

### 1.2 5 论点 → 6 章节规则

**规则**：N 个核心论点做成 N 章 + 1 个收束章。

- v1.0：选题卡有 5 个论点 → 写了 6 章（5 论点 + 1 收束）
- 少于 5 章则密度太高，多于 7 章则注意力分散
- 收束章不是总结——是形成最终判准的独立论据

### 1.3 反例权重原则

**规则**：反例只需要说清楚失败原因，不需要给细节。

**案例**：Fast Radius 段落从 7 行压缩到 4 行。删掉了"NYSE: FSRD""SEC 文件里的最后一句话"——读者不需要记住一个退市公司的 ticker。反例的核心功能是：用失败原因反衬成功路径。说清楚"数据不够 + 烧钱快"就够了。

**反例权重公式**：反例篇幅 ∝ 1 / 读者对该案例的熟悉度。越冷门的反例，越要压缩。

## 二、Drafting（写作阶段）

### 2.1 开场：场景 > 数据 > 判断

**规则**：第一段打开具体场景，第二段灌数据，第三段给判断。

**正例**：v1.0 开头——"2013 年，马里兰州小办公室"（场景）→ "$686.6M，1.65 亿零件"（数据）→ "把制造业报价做成了 API"（判断）。

**反例**：不要以"最近，AI 行业…"或"Xometry 是一家…"开头。场景让读者进入画面，数据建立信任，判断锁定注意力。

### 2.2 对比文章不用表格，用逐段展开

**规则**：四家公司对比 = 四段独立段落，不用 markdown 表格。

**为什么**：markdown 表格在手机屏幕上横向滚动，阅读体验极差。逐段展开给每个公司一个独立节奏——读者读完一段形成一个完整印象，再进入下一段。

**模式**：`**Model, Company.**` → 2-3 行公司描述 → 1-2 行数据 → 1 行判断。每个公司 5-7 行。

### 2.3 中美对照文的"防杠"技巧

**规则**：任何中美产业对比文章，必须在给完框架后立刻声明边界。

**模式**："当然，这三个约束不是完整解释。任何一个国家层面的产业差异都有几十个变量在同时作用——政策、教育、文化、地缘。这三个是本文基于 Xometry 赛道最显著的结构性对照，不是唯一解释。"

**为什么**：对比文天然容易触发"美国 > 中国"的简化版解读。边界声明让读者知道：作者承认复杂性，这只是三个最有解释力的变量。

**适用条件**：所有 pillar-4（中美双边视角）文章。

### 2.4 双案例交叉验证

**规则**：单一案例的论证天然脆弱。在判定性段落后，加一个不同行业的平行案例，证明模式的普适性。

**案例**：v1.1 在"B 端 AI 确定性 = 配对数据"段落后，加了肺结节检测 AI（Mayo Clinic 94%）。制造业 + 医疗两个行业同时适用同一框架，读者就无法说"这只是 Xometry 特例"。

**模式**："这其实不是 Xometry 独有的模式。[另一个行业] 也面临同样的结构——[具体数据]。B 端 AI 的确定性，永远建立在配对数据的积累之上。"

### 2.5 结尾从结论变为信号

**规则**：不要用结论收束，用信号收束。

**正例**："它提示了一件事：AI 平台经济，可能不是从最热闹的地方开始的。"

**反例**："它是 AI 平台经济的正确打开方式。"（暗示文章给出了答案）

**为什么**：公众号读者反感姿态。结论 = 你在告诉他们答案。信号 = 你给了一个观察，他们自己判断。

## 三、Quality（质量阶段）

### 3.1 Humanizer：8 条最高频 AI 模式

从 29 条 humanizer 规则中，009 踩中的 8 条（按频率）：

|---|---|---|---|
| 28 | Signposting | "这篇文章想讲清楚" | 直接提问 |

## 四、Publishing（发布阶段）

### 4.1 公众号标题 = 信任锚点 + payoff

**公式**：标题 = [信任锚点] + [payoff]

- 信任锚点：让读者相信这不是标题党。"12年亏出来的护城河"（12年 = 数据积累时间，"亏出来的" = 不是吹出来的）。
- Payoff：让读者好奇打开后能得到什么。"Xometry如何用AI把工程师经验变成印钞机"（印钞机 = 利益/价值）。

**反例**："差了一个 Xometry"——有悬念但缺信任锚点，读者不知道是干货还是标题党，不会点。

### 4.2 手机排版：bold 独立段规则

**规则**：每个 bold 独立段必须能独立承载核心论点的 80%。如果所有 bold 行去掉后文章依然完整可读，说明 bold 没打对地方。

**案例**：published 版把以下句子提为加粗独立段：
- "护城河是数据。"
- "是即时报价。"
- "Pure marketplace / 是这条赛道唯一被验证的规模化路径。"
- "B 端 AI 的确定性，永远建立在配对数据的积累之上。"

**为什么**：公众号是扫读媒介。读者滚动时只抓 bold 行，抓到了才停下来读上下文。bold 行是"视觉锚点"。

### 4.3 段落间距：2-3 句一个断点

**规则**：手机屏幕窄，连续 5 行无空行 = 用户跳过。每 2-3 句插入空行断点。

### 4.4 章节编号：01/02/03，不是一/二/三

**规则**：公众号平台用阿拉伯数字编号章节。中文数字笔画多，在小屏幕上拥挤，阅读效率低于阿拉伯数字。

### 4.5 去工具化引用

**规则**：公开发布内容里不能出现内部工具名。

| 禁止 | 替代 |
|---|---|
| "inbox 里列出的" | "另外三家" |
| "选题卡编号 007" | "我之前写的 'Agent 经济的完整回路已经出现'" |
| "draft v1.2 里" | 不需要——读者不知道什么是 draft |

**原则**：读者能接受的是"我之前写过的一篇文章"这类自然引用。作者和 agent 之间的协作语言（inbox/draft/topic card）在公开发布内容里全都不可见。

### 4.6 副标题价值

**规则**：读者打开文章后第二眼落在副标题上。副标题必须在 2 秒内给出核心 takeaway。

**模式**：`"Xometry 是全球第一个跑通'AI 即时报价 + 全球供应商网络'的 industrial marketplace"`——独立成行，加粗，放在标题和正文之间。

### 4.7 负数格式

`$(5.3)M` → `(5.3)M`。括号已表负数，不加 `$`。

### 4.8 数据来源 → 参考资料

"数据来源" → "**参考资料**"。更自然，不那么学术气。

## 六、011 贡献的新增模式（2026-06-16）

### 6.1 数字对比分母验证（Quality 阶段）

**规则**：任何 "A 是 B 的 N 倍" 句式，必须在同一句话里显式写出 A 和 B 各是什么。如果读者需要自行推断 A 或 B 的值，这个数字就是有问题的。

**案例（011 的 18.5x 错误）**：正文写 "2024 年优必选卖掉了 1,079 台"（公司全年总出货）+ "现在他们对同一个客户的 2026 年目标是 18.5 倍"。分子是比亚迪年目标（20,000），分母是优必选全年全量（1,079）。"同一个客户"的措辞让读者以为在比"比亚迪今年 vs 比亚迪去年"，实际上在比"一个客户的目标 vs 整家公司去年的总产量"。正确数字：20,000 ÷ 150 = 133 倍。

**模式**：`"现在他们对同一个客户的年目标从 150 台跳到了 20,000 台，133 倍。"`——A 和 B 在同一个句子里，读者不需要自行推断任何一个。

**为什么 AI review 发现不了**：contract review 的十二维度检查文风、结构、信源标注，不做数学验算。20,000 ÷ 1,079 的计算结果是正确的（18.53），错误的是分母对象的选取——这不是数学错误，是**对比配对错误**。AI 能验算 18.53 对不对，但不知道"同一个客户"不应该对 "1,079"。

**检查方法**：读取包含 "倍" 的句子 → 向前找最近的两个数字 → 列出这两个数字各是什么 → 确认对比对象在语义上一致。

### 6.2 "同一个客户" + 倍数 = 高危句式（Drafting 阶段）

**规则**："同一个 [主语]" + 倍数的组合，天然让读者把分子和分母都锚定到该主语身上。如果分母不是该主语的数字，必须改写——要么把分母改成该主语的真实数字，要么去掉"同一个"。

**案例**："同一个客户的 2026 年目标是 18.5 倍。" 分母 1,079 不是客户的数字，是公司的数字。

**修复**：把 "18.5 倍" 改成 "133 倍"（20,000 ÷ 150）。或者保留 18.5 倍但去掉"同一个客户"："比优必选去年卖给全世界的总数还多 18 倍。"

### 6.3 未验证数据禁止作为物理锚点（Research / Quality 交叉）

**规则**：凡是源标注"抓取失败 / 需下一轮深抓 / 未验证"的数据点，绝对不能成为正文的物理锚点——即不能成为"让读者看见画面"的核心描述。

**案例（011 的 32cm 错误）**：v1.0 中 "32 厘米" 的来源链是：V2 Subagent A（429 失败）→ 标注"ubtrobot.com/cn/ 抓取失败，需下一轮深抓" → 从未被验证 → 被写入 §01 作为物理锚点。整个 v1.0/v1.1 的"太小了连杯子都端不稳"这个画面建立在假数据上。Sixth Tone 后来证实 U1 是 183cm 全尺寸人形机器人。

**区分**：未验证数据可以作为**辅助信息**出现在正文（标注"据…报道，尚未独立核验"），但不能成为**物理锚点**——即读者看完文章后闭上眼睛能"看见"的那个画面。物理锚点必须来自已验证的一手源。

**操作**：定稿前逐句检查——哪些句子是读者闭上眼睛能"看到"的画面？每个画面的物理参数（尺寸/重量/颜色/动作）来自哪个已验证源？

### 6.4 写作窗口内浏览器实时验证（Research 阶段）

**规则**：热点调研型文章（C 类）在 draft 启动前或写作过程中，必须至少做一次独立第三方源的实时浏览器验证。验证的目标是：找到与已有数据**不同来源**的独立报道，交叉比对。

**正例（010）**：写作窗口内打开 HN item 48518684，获取实时 332 分/187 评论，验证改变了数据点（310→332）。

**反例（011）**：Sixth Tone 报道（2026-06-02 发布）在 v1.0 启动前就存在于互联网上。如果在 v1.0 启动前做了浏览器验证，32cm 假数据在第一个 draft 就会被发现。但它被推迟到了 v1.2——中间经历了三轮 contract review 和一次 humanizer pass，浪费时间在基于假数据的编辑上。

**操作**：在 topic card 的"关键素材"清单中，给每类信息标注验证策略——"知乎 API（已抓取）/ Sixth Tone（待浏览器验证）/ 港交所公告（已下载）"。未验证项在 draft 启动前必须至少完成一个独立源的交叉比对。

### 6.5 Contract review 盲区：数学验算与对比配对（Quality 阶段）

**规则**：contract review 的 AI agent 擅长文风、结构、信源标注检查，不擅长两件事：(a) 数学验算，(b) 对比类数字的分母对象配对是否成立。

**案例**：18.5x 错误通过了三轮 review（94→99→102），被用户用一句话指出。"同一个客户"是语义命题，不是数学命题——AI 能验算 20,000 ÷ 1,079 = 18.53，但无法判断"同一个客户"这个短语是否应该匹配分母 1,079。

**修复方向**：在 contract 评分流程中增加一个独立步骤——"数字对比配对检查"：提取所有包含"倍/倍于/X倍"的句子，显式列出分子和分母各代表什么，人工判断对比对象是否一致。这个检查不在 LF-1~LF-16 的评分范围内，应该在评分前单独跑。

### 6.6 Bold 独立段升级判据（Publishing 阶段，扩展 §4.2）

**规则**：draft 中的 `**bold**` 在微信发布版中有两种命运：(a) 保留为行内粗体强调，(b) 升级为独立粗体段落。升级的判据是——**这句话如果截图发朋友圈，能不能独立成立？**

- 能独立成立 → 升级为独立段落（前后各空一行）
- 只是段落内的强调 → 保留行内粗体

**案例（011）**：
- 升级："U1，10天，3800台。这是全球所有公开信息中，最大的一次 C 端人形机器人单次预售事件。"——截出来就是一条朋友圈。
- 升级："他们买的，大概率是一种介于人与宠物之间的陪伴。"——完全独立于上下文。
- 保留行内："**最大的一次 C 端人形机器人单次预售事件**"——需要前文 "U1 的 3,800 台是目前全球所有公开信息中" 才完整。
- 升级后的独立粗体段在微信中有两个功能：(1) 视觉锚点——读者滚动时停在这些句子上，(2) 分享锚点——读者截图转发的天然素材。

### 6.7 公众号表格使用边界（Publishing 阶段）

**规则**：表格在微信中可以用的前提：列数 ≤ 3、每格 ≤ 15 个中文字。超出任一限制，改用逐段展开模式（§2.2）。

**案例（011）**：可信度对比表（3 列 × 7 行，最长格 "多边形信号（5 家车厂 + 1 家家居 + 1 家物流）" = 18 字）——刚好在边界上，手机端勉强可读。

**对照（009）**：四家公司对比（4 列）→ 用逐段展开，不用表格。超过 3 列的表格在手机上横向滚动，阅读体验极差。

### 6.8 参考资料微信版精简规则（Publishing 阶段）

**规则**：draft 中的详细 URL + 核验注文 → published 中精简为出处 + 核验状态。删除三项：(1) 完整 URL（微信不支持外链），(2) "文中所引…均来自此报告"的重复说明，(3) 对同一来源的冗余描述。保留两项：(1) 出处（能定位到的程度），(2) 核验状态（"待交叉验证""二手报道数据"）。
